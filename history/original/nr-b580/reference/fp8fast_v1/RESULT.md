## 1. 调研部分（14:48 那版，保留）

### 1.1 调用计数与分段

**`quantize_fp8` 每次调用 = 1 次 `_kernel` 启动，383 次/帧**（与 `FRAME_BUDGET_REPORT.md` §5.3 完全一致）。

| 段 | ms/帧 | 占比 | 性质 |
|---|---:|---:|---|
| `x.half()` | 0.372 | 0.48% | 纯 CPU（dispatch） |
| `.contiguous()` | 0.539 | 0.70% | 纯 CPU（已连续时是 no-op） |
| `torch.empty_like()` | 1.930 | 2.50% | 纯 CPU（分配） |
| **`_kernel` 启动** | **74.52** | **96.33%** | **含等 GPU 队列** |

**外围三项合计 2.84 ms/帧，纯 CPU。** numel 分布：中小张量（≤1M 元素）占 **76%** 的调用（291 次/帧）。

### 1.2 ⚠️ 报告 §8.2 第 1 行的建议需要修正

报告写"提高每次启动的行数/批大小 ⇒ 启动次数减半 ≈ 3.8 ms"。**这一步逻辑跳跃。**
`_kernel` 的 grid 是 `cdiv(numel, 512)`，改 `B` 只改 **grid 大小**，
**不改 Python 侧的调用次数** —— 启动次数 = `quantize_fp8` 的调用次数 = 383，与 `B` 无关。
要减次数必须**合并 383 个散布在 6 个文件里的串行依赖调用 = 改模型结构**。

（附带：`_round_fp8_half` 是**逐元素**函数 ⇒ 改 `B` 不会改字节。报告 §8.3 那句
"任何改行数/批大小的动作都会改变 K 累加顺序"**对本例不适用**。）

| ~~报告四分区合计~~ | ~~**68.50**~~ |

⇒ 只采用**计数**、**同口径相对占比**、**纯 CPU 段的绝对毫秒**；**绝对总量一律不引用**。

## 2. 三把刀是什么（`fp8fast_cuts_v1.py`）

| 刀 | 机制 | 微基准定价 |
|---|---|---|
| **`disp`** | 分发器每次调用做四件固定事：`x.device.type=='xpu'`（278.6 ns）、函数体内 import（78.5 ns）、backend 查询（29.4 ns）、计数（35.5 ns）= **421 ns/次**。切法：`x.is_xpu`（34.7 ns）+ import 缓存 ⇒ **108 ns/次** | 省 **313 ns/次** |
| **`half`** | `source = x.half().contiguous()`，**入参绝大多数本来就是 fp16 且连续**。切法：`x if x.dtype is torch.float16 else x.half()` | 省 **170 ns/次** |
| **`pool`** | `output = torch.empty_like(source)` 每次 **5.04 µs**。切法：按 `(shape,dtype,device)` 池化，**只在池里那个缓冲确实无人持有时才复用**（`getrefcount(buf)==3`） | 省 **5.04 µs/次**（理想） |

**`disp` 必须按身份重绑**（调用点写的是 `from .pre_mlp import quantize_fp8`，别名 `q` 用名字扫不到）；
**`half` 必须先判后跳**（确有 fp32 入参与切片视图）；
**`pool` 的安全性靠「单流 + 引用计数回到基线」论证**。

## 3. 实验设计

**10 臂回文**（位置平衡、无残余顺序偏置）：

```
位置 1..10:  off disp half pool all | all pool half disp off
r1 = 位置 1..6（off disp half pool all all）
r2 = 位置 7..10（pool half disp off）
```

- 协议照抄 `rows_bench_v1.py`：分进程、4 帧热身、统计帧 4..N、计时期禁 JIT、**每帧逐字节校验**
- **所有臂都对同一个冻结参考做字节门**（`D:/fullsize-rows-v1/r1/full-both/validation.json`）
- **所有臂都让第一层 `hostfast` 关着** —— 本层削的是 ATen 侧固定开销，与第一层的
  `JITFunction.run` 缓存**机制不重叠**，让每臂落在同一地基上
- 单臂 ≈2.5 分钟 ⇒ 分两个租约（`gpu_lease_nr.py` 硬上限 1800 s）

**为什么是 5 个臂而不是 off/on**：三把刀机制不同、量级差一个数量级。只报 off vs all 的话，
一旦 all 偏离预期就**无法判断是哪一把刀没生效**。

### 3.1 ⚠️ 中途失败与修复（诚实记录）

## 4. ⚠️ 汇总脚本的两个真 bug（本轮修掉）

### 4.1 残缺轮次被当成有效数据

失败轮次**也会留下 `validation.json`**（含 `error` 字段、`timing=null`、`identical_frames=null`）。
初版没有闸门，于是 `sorted({r['identical'] ...})` 在 `int` 与 `None` 之间比较时**崩溃**；
更坏的情况是它**不崩**、把残缺臂的计数混进平均值。

**修**：`usable = timing.median_ms is not None and identical_frames is not None and not error`，
并把被排除的轮次**打印出来**（`← 残缺，已排除`），不静默丢弃。

### 4.2 ★ 均值口径被 session 漂移污染（本轮最重要的方法学发现）

**实测存在 session 级偏移**：同一臂在 r1 与 r2 的中位帧墙不同，**四个臂全部 r2 更慢**：

| 臂 | r1 | r2 | 差 |
|---|---:|---:|---:|
| `off` | 82.5745 | 83.1659 | **+0.591** |
| `disp` | 82.5517 | 83.2502 | +0.699 |
| `half` | 82.3491 | 83.4620 | +1.113 |
| `pool` | 83.0731 | 84.1213 | +1.048 |

**四个臂同号 ⇒ 是 session 偏移，不是巧合。**

而 `all` **只出现在 r1（较快的那个 session）**。于是「均值之差」把 `all` 算成
**省 0.294 ms** —— **纯属假象**。正确的配对口径是 **亏 0.589 ms**。

**修**：新增**配对口径**（先在 session 内算 `arm − off`，再跨 session 平均），
并报出「该臂出现在几个 session」；出现次数少于对照臂的一律标 **`否 ← 不进结论`**，
并在脚本里直接点名"均值之差表里它的数是漂移假象，不得引用"。

**⇒ 通用规则：跨 session 的因子对照必须先在 session 内配对。**
回文只保证"每个位置在两个半程各出现一次"，**它不能修一个臂缺席某半程的情况**。

## 5. 结果（配对口径 —— 结论以这张表为准）

| 臂 | r1 内 saved | r2 内 saved | **平均** | 符号一致 | 出现在几个 session |
|---|---:|---:|---:|---|---|
| `disp` 只拆分发器 | +0.023 | **−0.084** | **−0.031 ms** | **不一致** | 2/2 |
| `half` 只拆空 half dispatch | +0.225 | **−0.296** | **−0.035 ms** | **不一致** | 2/2 |
| `pool` 只拆 `empty_like` | −0.499 | −0.955 | **−0.727 ms** | **一致** | 2/2 |
| `all` 三把全拆 | −0.589 | （未测） | −0.589 ms | — | **1/2 ← 不进结论** |

（正数 = 比 `off` 省；负数 = 比 `off` 慢。同变体跑间极差 0.59–1.11 ms = 0.7–1.3%；
报告里的"噪声地板 2.8%"是跨 session 口径。）

**逐条读：**

1. **`disp` / `half` 的收益 = 0。** |Δ| ≤ 0.035 ms（**0.04%**），且**两个 session 符号相反**。
   微基准预测 313 / 170 ns/次 × 383 次 = **0.12 / 0.065 ms** —— 预测的量级是对的（就是小到测不出），
   但连方向都不稳。**⇒ 这两把刀不值得留**（它们要改 9 个调用点的重绑，风险 > 0，收益 = 0）。
2. **`pool` 净亏 0.727 ms，两个 session 同号**（−0.499 / −0.955）⇒ **唯一可复现的效应，而且是负的。**
   机制：命中率 **55.06%**，**44.9% 的调用被拒**（调用方还持有上一个缓冲）——
   那 44.9% 白付记账、还得照样分配。且它长期占住 **119.1 MB**（68 个键），
   缓存分配器永久失去这部分可复用性。
3. **`all` 净亏 0.589 ms**（r1 内配对）：比"三把独立之和 −0.793"没那么糟 ⇒ 池的亏损与
   disp/half 的微小正向被部分抵消。

⇒ 三把刀**都不改字节**（设计如此）。**但"不改字节"只是必要条件，不是收益。**

## 6. 决策

**⇒ 第五层整层砍掉。** 三把刀没有一把值得留：

| 刀 | 收益 | 风险 | 判 |
|---|---|---|---|
| `disp` | 0（噪声内，符号不稳） | 改 9 个调用点重绑 | **砍** |
| `half` | 0（噪声内，符号不稳） | 需逐处确认入参 dtype | **砍** |
| `pool` | **−0.727 ms** | 唯一有内存别名风险 | **砍** |

**本轮不改产品代码**（这一层本来就没装到产品上，只在自己的轮目录里预跑）。

### 6.1 对优化路线图的影响

**⚠️ 「削每笔固定开销」这条路已经走到头。** 本层的三把刀覆盖的正是这条路的三个典型代表
（分发器判断、空 dispatch、分配器），合计 383 次/帧 × 每笔 0.3–5 µs。

- `disp` + `half` 一共只有 **0.19 ms** 的名义上界（383 × 0.49 µs），实测 **0**。
- `pool` 的 1.93 ms 名义上界被"45% 被拒 + 记账成本"吃光并倒亏。

**⇒ host 余量还剩 ~8.3 ms，但剩下的项都是这个量级或更小。**
`executor.py:80/83/85` 的形状/切片开销（213 op/帧）要凑到 7.8 ms 需要 **37 µs/op** —— 不合理。
**⇒ 结论：靠"省每笔固定开销"拿不到下一个 10 ms；要再往前只能动结构（减少每帧 2075 次派发）或设备侧。**
