## §0 一句话

把快速线的 dense 走到 `fast_matrices_v3` 的 W8A8 INT8 路径上，**设备忙时不是变快，而是 +4.9636 ms（+13.3%）**；
而**每一毫秒都来自「每次调用重新量化激活」**（新内核 `_quantize_rows`，+5.1791 ms），
**INT8 矩阵乘本身一分钱没省**（`_matmul` 6.7996 → 6.8144 ms）。

⇒ **A 的生死判完了：A 死。** 它连自己那 6.80 ms 的人口都动不了，9–14 ms 更无从谈起。

## §2 装置与刀：为什么这一次是可归因的

### §2.1 刀只能落在 `FastMatrices.dense`

`select('int8_dense')` **不是**一个干净的实验 —— 它会同时翻转三处都以 `mode == 'fp16_xmx'` 为条件的闸门：

1. `current_dense_tiled_provider_v1.CurrentDenseTiledMatrices.dense` —— POLICY tile 路径关闭；
2. `k8_tiled_provider_v1.K8TiledMatrices.dense` —— K8 精确点不再走 `_tiled_dot`；
3. `batched_branched_mlp_v1.apply` —— **整个批量分支 MLP 退回原实现**（`self.original`；`_pairs` 3.77 ms + `_project` 0.47 ms 会整块消失）。

⇒ 计数变化集里会混进与 A 无关的大块位移，**Δ_C 不可归因**。这是混淆，不是实验。

### §2.2 实际用的刀

**运行期类方法替换**（产品源 0 改动）：

```
FastMatrices.dense  →  包装器：
    if self.mode == 'baseline' or chunk_k == 8:      → 逐字委托（两臂完全相同）
    packed = self.packed[id(w)]（命中）或 None
    return fast_matrices_v3.dot(a, w, initial=initial, int8=True, packed=packed)
```

配 `provider.prepack(model)`（205 个缓冲、40.58 MB、0.39 s，会话建立时一次）。

**mode 保持 fp16_xmx** ⇒ §2.1 的三处闸门**行为逐字不变**；唯一改变的是**已经落到 FastMatrices.dense 的那批调用**。

### §2.3 装置透明性（P1 实测）

off 臂**每臂 12/12、两臂合计 24/24 帧**对冻结快速产物逐字节相等（`max_abs` 恒 0）⇒ 补丁机制在关掉时是透明的。

## §3 A 的真实可达人口 —— 对上游 §6 的定量更正

`to_single_digit_v1` §6 行 A 写「8 个 C32 dense/投影 走 INT8 XMX」，引 **23.1 ms / 305 次 = Triton 的 76%**。
但 A 的机制是 `fast_matrices_v3` 的 `int8_dense` 路径，**它只能碰到走 fused_dot 的调用**。

用上一轮落盘的 `launch_sites` 逐条核实（零 GPU）：

| 模块 | 启动/帧 | 发射点 | 走 `fused_dot`？ |
|---|---:|---|---|
| `fast_matrices_v3._matmul` | **115** | `fast_matrices_v3.py:94` ×115 | **是（全部）** |
| `batched_branched_mlp_v1._pairs` | 36 | 本模块 :77 | 否 |
| `batched_branched_mlp_v1._project` | 36 | 本模块 :80 | 否 |
| `fused_c32_projection_native_half_v1._kernel` | 10 | 本模块 :79 | 否 |
| `fused_swin_core_native_half_v1._kernel` | 10 | 本模块 :87 | 否 |
| `fused_c32_mlp_lut_v1._kernel` | 10 | 本模块 :53 | 否 |
| `fused_qkv_pack_native_half_v1._pack` | 52 | 本模块 :80 | 否 |
| `window_block_projection_v3._project` | 36 | 本模块 :56 | 否 |
| `window_block_attention_v3._kernel` | 36 | 本模块 :50 | 否 |

⇒ **A 的可达人口 = 115 次/帧、设备 6.7996 ms/帧 = 本臂 Triton 合计（32.4221 ms）的 21.0%。**
§6 那一行把 8 个模块记作一个整体，**高估了 A 的可达面 3.3 倍**（23.1 ms vs 6.80 ms）。

⚠️ 口径：本轮的 6.7996 是**本轮 off 臂 6 帧的均值**；§2 的 **6.3236 是最小口径**。两种口径不同，不可混用。

## §5 int8 的代价分解 —— 钱全花在量化上

| 族 | off ms | on ms | Δ ms |
|---|---:|---:|---:|
| `_matmul`（矩阵乘本身） | 6.7996 | 6.8144 | **+0.0148** |
| `_quantize_rows`（每次调用重新量化激活） | 0.0000 | 5.1791 | **+5.1791** |

**⇒ INT8 矩阵乘不比 FP16 快（差 +0.2%，在噪声内）。省下的一切都不存在，而量化又多花 5.18 ms。**

这直接解释了 `a_recheck_v1` 在 864x480 上量到的「慢 11–23%」：那里的 dense 人口更大，
但机制是同一个 —— **W8A8 的激活量化是逐调用的一次额外内核，而 int8 矩阵乘没有回报。**

## §6 质量

| 臂组 | 帧数 | 逐字节相等 | max_abs 最大 | rmse 均 | PSNR 均 | PSNR 最差 |
|---|---:|---:|---:|---:|---:|---:|
| off | 24 | **24/24** | 0.000000 | 0.3486 | 58.43 | 52.06 |
| on | 24 | **0/24** | **0.022949** | 0.3504 | 58.50 | 50.50 |

⚠️ **口径警告：这里的 PSNR 不能用来判「画面没变」。**
`rmse`/PSNR 是 harness 对**模型自身 exact** 算的 —— 两臂离 exact 都同样远（off 自己就与 exact 差 PSNR 58.43），
所以它对两臂之差**不敏感**。真正的判据是**对冻结快速产物**的读数：
off 逐字节相等、on 一个都不相等，`max_abs` 最大 **0.022949 ≈ 5.85 灰阶**。
⇒ **画面确实变了**（`int8_dense` 从设计上就改数值，`fast_matrices_v3.py` 头注明写
"deliberately NOT bit-equivalent"）。本轮只**报告**，**不判合格** —— 容差门归 D5 第 3 项（仍未裁定）。

## §8 一处未解决的口径差异（照实登记）

刀自带的调用计数器读 **171.2 次/run**，而 namer 与 profiler 两个仪器都说每帧 **115** 次 `_matmul`。
比值 1.49，**我没有把它对上**。

* 两个**独立**仪器（host 侧 namer、设备侧 profiler）**互相吻合**，且与 off 臂的基线吻合
  ⇒ 冲突方是刀自己的计数器。
* 该计数器**不参与任何判据**（P2 用的是 namer），判决不受影响。
* 一个**未验证**的猜测：计数器覆盖全部 15 次模型运行（12 次未剖析 + 3 次剖析），
  而未剖析的早期帧可能走了更多 dense 调用；剖析帧的 `_matmul` 次数在**两臂、六帧上都是 123**，完全稳定。
* ⇒ **登记为边界，不当作结论**。

## §9 边界

1. **诊断，不是证据跑**：不产正确性产物、不进任何门槛、不写 fastpath、**不作 fps 证据**。
2. **设备读数不回答帧墙传导**：那是 `fullchain_timing_v1` 的模型推断。本轮只说「设备侧这一刀净增 4.96 ms」。
3. **产品源 0 改动、冻结缓存 0 改动**（`D:/fullsize-rows-v1/r1/triton-cache` mtime 保持 2026-09-20 13:10:45）；
   刀只活在进程内存里，缓存副本另建在 `D:/a-insitu-v1/cache`。
4. **绝对毫秒只在本轮同索引间可比**；禁止跨轮引用（骨架里 §2 的 6.3236 是另一口径，已标注）。
5. **harness 每帧被处理两次**（`one_frame` 一遍 + `profiled_frame` 一遍）：`profile_pass_tail` 补丁只换了
   `report['cache_hits']` 一行，原循环仍在。对设备读数无害（每剖析帧各自成行），但刀的计数器必须按
   `model_runs` 摊分 —— 见 §8。

## §10 结论与建议

**A 到此为止。** 三条独立理由：

1. **可达人口比上游估计小 3.3 倍**（6.80 ms，不是 23.1 ms）；
2. **即使把整个 _matmul 人口变成免费，也只有 6.80 ms**，与 9–14 ms 无关；
3. **实测方向相反**：+4.96 ms，且**代价全在量化、收益为零** —— 在快速线上独立复现了 864x480 的结论。

**这一轮给出的可复用知识**：
* `int8_dense`（W8A8）在本装置的几何上**矩阵乘零收益**，任何以它为卖点的路线都应先被怀疑；
* 「每次调用量化激活」的**固定成本是 127 次内核 / 5.18 ms**，与人口成正比 —— 这是 W8A8 类方案的通用陷阱；
* `launch_sites` 是把「内核短名」钉到「模块」的可靠桥（本轮用它把上游的 8 模块混淆拆开了）。

**到个位数 ms 的路径现状**：A 已否证；C（L3-1）已确认是 1–2 ms 零钱；**只剩 B**（提交数 1266 → ≤300）。
B 仍卡在你手上两件**非技术**裁定：D5 三件事（尤其**容差门是否数值化**）与**任何改画面的落地审批**。

## §11 复现

```
bash reference/a_insitu_v1/a_insitu_run_v1.sh          # 五臂：00-warm-on + ABBA off/on
python reference/a_insitu_v1/a_insitu_report_v1.py --root D:/a-insitu-v1/r1
```

  驱动脚本**不用 set -e**，只以报告是否落盘判成败。
