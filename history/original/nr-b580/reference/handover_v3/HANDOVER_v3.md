### 1.2 ★★ 头号环境坑：本机 rmdir 会「递归上溯删除」

**这是本项目最危险的一件事，已经吃掉四棵树。**

* **机制**：本机卷上 `os.rmdir(非空目录)` **不抛错，直接递归删掉整个目录**。`os.removedirs`、`shutil.rmtree`、以及任何依赖「rmdir 遇非空父目录会抛错」来停下的代码，语义一坏就**从目标路径一路上溯删到根**。
* **引爆点**：Triton 的 `runtime/cache.py` 里 `FileCacheManager.put()` 末行调用 `os.removedirs(temp_dir)`，而 `temp_dir` 位于 `<TRITON_CACHE_DIR>/<key>/tmp.pid_*/` ⇒ 若 `TRITON_CACHE_DIR` 落在交付物树内部，上溯链正好穿过整棵树。
* **四次事故**：
  1. `D:/fullsize-rows-v1`（Triton 缓存在树内）
  2. `E:/.../nr-b580/.git` 被掏空（`refs/`、`logs/`、`worktrees` 全没，**历史不可恢复**）
  3. `G:/nr-4way-v1` 全树（8015 条记录，已按记录无损还原）
  4. `D:/corr-strip-v1` 全树（13,695 条记录，已无损还原，且**在还原数据上重跑报告器得到逐字相同的结论**）
* **本机 WorkBuddy 的安全删除沙箱把批量删除改判为「移入回收站」**，所以这四次数据都是**搬走**而非销毁 ⇒ 能还原。但这**不是**可以依赖的保障。

**铁律（不可协商）**：

1. **永不**对交付物树执行 `rmdir` / `rmtree` / `removedirs`（哪怕只删一层空目录）。删中间文件用 `to_recycle_v1.py`（见 §7）。
2. **任何缓存与临时目录都不许落在交付物树内部**（`TRITON_CACHE_DIR`、`TMP`）。默认缓存仅约 156 KB，搬到树外极便宜。
3. **每个会 import triton 的新脚本，必须在 import 之前装缓存守卫并自检生效**（`rows_fscache_guard_v1.install()`）。
4. 清中间产物一律走**回收站**，不走 `rm`。
5. git 的危险动作**不是 commit，而是删 ref**：禁用 `branch -d` / `worktree remove` / `update-ref -d`。

**现成补丁**：`G:/nr-4way-v1/scripts/triton_cache_fix_v1.py`（自测 11/11）——把临时文件改成目标路径的同目录兄弟，不再建临时目录，因此不再需要 `removedirs`；`PermissionError` 先重试 6 次，重试全挂时**只有目标确实已存在**才允许放弃，否则抛错，绝不静默。另含 `assert_cache_safe()` 拒绝把缓存放进受保护树。
**还原工具**：`corr_strip_v1/restore_from_recycle_v1.py`（默认 dry-run，全程只用 `os.rename`）；手法见用户级技能 `windows-recyclebin-tree-restore`。

### 1.5 送审流程（本项目的核心工作方式）

**画面变更 = 先落地后送审**（2026-09-21 裁定，取代旧的「先审批」）：落地 → 出送审包 → 通知审核 → 用户可否决要求回退。
送审包 = 前后 sha256 + 逐字节记录 + 速度配对差 + D1/D2/D3/R1 表 + **三支对比视频**。
**一次只送一块**（「不要攒多块一起看」）。
容差门**不数值化**：D1/D2/D3 只作自动预筛，R1 只报告。

**这一节请逐字读完。本项目历史上最贵的错误全都是口径错误。**

### 2.1 五把不同的尺

| 名称 | 定义 | 怎么测 | 能不能外推 |
|---|---|---|---|
| **帧墙** | 单帧从起到落的墙钟，稳态窗口取中位（通常 `frames[4:]`，去上传/回读/IO/编解码） | 243 帧运行，同链 ABBA | ✅ 唯一作加速比证据的尺。**必须注明装置与帧数** |
| **设备忙时** / `gpu_busy_ms` | 设备上内核占用时间之和 | 设备侧在场剖析，窗尾 3 帧 | ⚠️ 只说设备侧，**不回答帧墙** |
| **Triton/ATen 最小口径** | 跨帧对每个 (module, grid) 取**最小值**再求和 | `single_digit_minruler_v1.py` | ⚠️ **乐观下界**，没有任何一帧真的做到。只能排序定位，**不作证据** |
| **完美重叠地板** | 把主机侧全部拿掉后测得的帧墙 | `interopipe_v1`（有无逐帧 `synchronize` 为唯一变量） | ⚠️ 见 §2.2 警告 |
| **孤立微基准** | 单次启动的 XPU 事件计时，再乘每帧次数 | 微基准 | ❌ **只作量级，绝不可外推**。已两次翻车（见 §4.4） |

### 2.2 ⚠️ 地板 43.35 ms 已经过期

`interopipe_v1` 于 **2026-09-20** 实测完美重叠地板 = **43.3481 ms**，并据此撤回了旧稿「硬底 36.62 ms = 27.3 fps」（36.62 是内核时间之和，而占用率 ≠ 吞吐）。

**但 09-22 的四路测量里，产品默认态帧墙已经是 42.97 ms —— 比那条「地板」还低。**

⇒ **43.35 不能再当现状天花板引用。** 它要么随之后四次设备侧落地而下移了，要么与 42.97 不同口径。
**接手第一件事就是重新量一次地板。** 在量出来之前，任何「已经到地板了，没得做了」的结论都不成立。

### 2.3 图重放：出货开着，测量关着

快速线有一条图重放路径（`graph_front_v1.py`，`torch.xpu.graph()` 录整帧、之后每帧 `replay()`）。

* **生产装图**：`product/nr_runtime_v1.py` 的 `Session.process` **装全部组件含图**。
* **测量排图**：`materials_entry_v1.py` 显式排除 `stack.graph` 等 ⇒ **计时窗跑的是 eager**。这是硬门：13 个 stage 窗口靠 host 侧 `mark()` 同步，图重放没有 host 阶段边界，不排除会导致窗口不再互斥、报告全废。
* **收益**（1080p 同轮配对，输出逐字节等于已审核输出）：精确 1.013×、FP16 XMX 1.195×、INT8 **1.240×**。
* **出图原理**：建图一次（输入 clone 进静态缓冲 + 预热 + 录图），之后每帧只 `copy_` + `replay()`。省掉的是**主机侧 Python/Triton 提交**，设备侧内核照跑。
* **逃逸口**：`forward()` 开头 `if progress is not None or current_arithmetic_backend() != 'triton': return self.original(...)` ⇒ **带进度回调就回退 eager**。这就是 stage fence 与图不兼容的根因。
* `key` 含 shape/dtype ⇒ 换分辨率或 dtype 另建图；`_validate()` 一变就抛错（须新建 session）。

**★ 后果**：**所有主机侧的刀，其收益在出货配置下不可外推**（图重放已经把这些提交绕掉了）。
**每份快线 A/B 报告都必须写明「graph 排除、eager 口径」。** 这是本项目最容易自欺的地方。

## 4. ★★ 否证登记：这些别再试

### 4.1 INT8 / XMX 全系：在本代硬件上已被否证

| 尝试 | 结果 | 出处 |
|---|---|---|
| 快速线 dense 走 W8A8 INT8 XMX | 设备忙 **+4.9636 ms（+13.3%）**，效应/不确定度 9.5× ⇒ **否证** | `a_insitu_v1` |
| 整线 W8A8 INT8 | 慢 **11.4%**，PSNR 低 **9.62 dB** ⇒ **严格被支配** | `a_recheck_v1` |
| 「多用 XMX」总账（8 次尝试） | **8 次全慢**：FP16 XMX 混合 0.670–0.822×、INT8 8×16 +84%、整数乘积 3.78–4.05×、无损 INT8 数位拆分 10.78×、局部 INT8 投影 +127%/+96%、整线 W8A8 慢 11.4%、快速线 W8A8 +4.96 ms | `xmx_consistency_cost_v1` |

**根因（这一条极重要）**：代价全在**包装**——`_quantize_rows` 127 次/帧 = +5.1791 ms，而 int8 矩阵乘本身**零收益**（`_matmul` 6.7996 → 6.8144，Δ **+0.0148**）。
**删掉保一致层后纯 DPAS 快 8.0×，但整圈（无损判断 + 分类 + 转换 + 还原 + 修正）永远是净亏。**
INT8 在总账里只占 23% 的分母 ⇒ **瓶颈是包装，不是算力**。

⚠️ **一个重要修正**：`int8_upside_v1` 指出——**INT8 只被「未融合」实现否证**。未融合版 +5.1791 ms 已否证，**融合版从未做过在场测量**。不要用未融合的结论外推融合版。

### 4.2 保一致层（corr_strip）：不是税，是更优实现

曾在**一个完整实验**里验证「为对齐 4060 舍入而写的修正原语是性能税」这条假设。**结论：否证。**

| 判据 | 阈值 | 实测 | 判定 |
|---|---|---|---|
| **P1**：`nat` 臂（换原生原语）设备忙 Δ | > −1.0 ms 即判「换原语无用」 | **+1.7835 ms（更慢）**，效应/不确定度 **18.8×** | ❌ 判负 |
| **P2**：`alg` 臂（再去掉 XOR 归约树）Δ | > −3.0 ms 即结案 | **数学上必败**：`_normalize` 仅 0.0503 ms，清零也 ≈ +1.77 ms | ❌ 未跑即败 |

* 归因：差集中在 4 个承载修正原语的模块（合计 **91%**），**启动次数逐帧相同** ⇒ 差来自内核体，不来自派发。
* **机制**：`tt.fp_to_fp → fp8` 在 Intel XPU **不是硬件指令**，展开成约 **20 条软件序列**（`llvm.nearbyint.f16` + `usub.sat.i16` + `umin.i16` + `uitofp`/`fptoui` + `fmul half`），逐 lane 标量、跨整数与浮点管道。复刻层全程 **i32** + 原生 `umin/umax.i32` ⇒ **指令更多（LLIR 208 vs 164）却更快**。
* **★ 教训：指令条数不是成本，指令种类才是。**
  （同源现象：INT8 XMX 之所以慢，也是因为 B580 上整数 ALU 比硬件 fp8 cvt 快。）
* ⚠️ **口径坑**：同一内核 **TTIR −80%** 而 **LLIR 只 −21%**，**两者都不能预测速度**。
* **画面**：`validation.json` 每帧带输出 `sha256`，逐帧比对——**两对 off/nat 臂 12/12 帧输出逐字节完全相同**。⇒ 保一致层既不改画面，又比替代方案快 1.78 ms。

### 5.3 ATen 侧

`aten::copy_` **1.3192 ms（173 次）** + `aten::mul` **1.0375 ms（89 次）** = ATen 最小口径的 **68.8%**。

### 5.4 机器尺子（Arc B580 实测，09-22）

| 量 | 值 |
|---|---:|
| 设备 | 160 EU / 20 subslice，max work group 1024，sub group {16, 32}；torch 2.13.0+xpu，triton 3.7.2 |
| 渐进带宽 | **389.7 GB/s** |
| 每块边际成本 | **11 ns / 块**（块 = 1024 fp16 = 4 KB） |
| 每启动固定成本 | **13.7 µs** |
| 同工作量只换切法 | **2.358×** 差 |

自洽性：11 ns/块 ÷ 4 KB = 390 GB/s，与实测渐进带宽相等 ⇒ 该形状已贴住 roofline。
⚠️ **必须否掉的估算**：「形状浪费 8.57 ms/帧」不成立（口径产物，因为块的工作量本身随 grid 变）；「W = 160 / wave 可捡 1.02 ms」也不成立（并发曲线从 grid 1 到 2048 **单调线性、没有拐点**）。

### 5.5 五条反直觉的教训（写进肌肉记忆）

1. **看代码猜冗余会被证伪**。以为「跳过冗余 `.half()` / `.contiguous()`」能省，实测**根本不进 dispatcher**。真挖出 −3.86 ms 的是**按值恒等率普查**（383 次里 191 次恒等 = 49.9%，按调用点完美二分：13 点 100% / 29 点 0%）。
   ⇒ **方法学：混合均价不能给子集定价。**
2. **指令条数不是成本，指令种类才是**（见 §4.2）。
3. **TTIR / LLIR 变化不能预测速度**（TTIR −80% 而 LLIR 只 −21%，速度却无收益）。
4. **孤立微基准不能外推**，符号都能反（切法 −2.40 → 实测 +5.54）。
5. **跨轮引用毫秒前，先读那张表的符号约定**。本项目同一份文档内 `+` 的含义在「省」与「代价」之间**并不统一**（例如 `motion_scope_land_v1` 是「正 = 省」，`corr_strip_v1` 是「正 = 代价」）。**已因此误报过一次「方向冲突」。**
