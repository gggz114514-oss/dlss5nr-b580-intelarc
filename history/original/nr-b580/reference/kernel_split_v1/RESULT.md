## §0 一句话

**合并名拆开了：** `_kernel` **是 8 个模块，不是 1 个**。 而拆开之后发现一件比拆名本身更重要的事：
**归因（是谁）与次数完全可复现，定价（值多少）不可复现** —— 同一模块、同一 grid、同一次启动，
相邻两帧之间可以差 **19 倍**，而帧的设备总忙时只差 2.1%。
⇒ **模块清单可以直接用；毫秒排名只能读量级，不能读名次。**

## §2 方法：复用**已有**装置，不重造

逐字复用 `fullsize_devsplit2_v1/rows_devsplit2_v1.py`（82 ms 时代已解过同一问题），
只把挂载点从 `rows_attrib2_v1.py` 换成当前线的 `materials_v1/materials_entry_v1.py`：

包 `JITFunction.run`，在**启动时刻**按顺序追加 `f'{inner.fn.__module__}.{inner.fn.__name__}'`（+ grid）；
chrome trace 提供每个内核的**设备时长**；队列单流有序（`pid=0 / tid=64`）⇒
**第 k 个内核事件 = 第 k 次记录**。名器装在 `with profiler` **内部** ⇒ 不存在"记了没 trace / trace 了没记"的窗口差。

### §2.1 两条必须先排除的风险（都已实测排除）

* **产品层 1 会不会绕过？** —— `NR_LAUNCH_FASTPATH` 的 `run` 刀替换的正是 `JITFunction.run`
  （`nr-b580-int8/experimental/launch_fastpath_v1.py:155-165`），但它只把准备阶段换成查表、
  **不绕过** `run` **本身** ⇒ 名器在它之后安装、成为最外层包装。**由 C1/C2/C6 三条自检复核，不靠推理。**
* **产品源码 0 改动**：补丁 + exec，进程退出即消失；`materials_entry_v1.py` 里 `@triton.jit` 计数 = 0
  ⇒ 不移动任何内核起始行号 ⇒ 冻结磁盘缓存仍有效，**计时期不引入 JIT**。
* **冻结缓存只用副本**（`D:/kernel-split-v1/cache`），`D:/fullsize-rows-v1/r1/triton-cache` 一个字节未动。

|---|---|---|---|

### §3.1 ★ 残差被完整闭合（额外收获）

C4 的 81.4 µs 缺口**不是噪声，是一笔可指认的账**：

```
key_averages 的非 _ZTS 实例 = 794
  = 776 真 Triton 启动（JITFunction.run 记录、trace 落盘）
  + 18 次 Memcpy（Memcpy D2D 12 次 0.0738 ms ＋ Memcpy D2M 6 次 0.0075 ms = 0.0813 ms）
      ↑ trace 把它们记在别的 cat 下，所以不进 `cat == 'kernel'`
```
**0.0813 ms（memcpy）≈ 0.0814 ms（闭合残差）** —— 精确对上。
第三重独立佐证：驱动级 `urEnqueueUSMMemcpy` **恰好 18 次**。
并且 **1266 次驱动级内核提交 = 776 Triton + 490 ATen**，逐项相等。

### §3.2 ATen 侧 100% 链上

`External id` 反查（ATen 事件**有**这个把手，Triton 事件没有）：
490 个事件 **全部链上（未链上 0 / 0.0 ms）**，合计 **6.9755 ms**，与 `key_averages` 报的 **6.9755 ms** 相同。

## §6 ★★ 判据（本轮最重要的一条）：归因可复现，**定价不可复现**

为判别"同 grid 差异"是**数据相关耗时**还是**测量不稳**，我加跑了一帧（`LIMIT=31` ⇒ 剖析**相邻的第 30 帧**）。
两帧同 session、同环境、同帧号相邻：

### §6.1 可复现的部分（硬）

| 事实 | 读数 |
|---|---|
| **模块清单与逐模块启动次数** | **三帧（2 / 30 / 31）逐项完全相同**（32 个模块，`count` 一个不差） |
| 设备总忙时 | 45.8101 → 46.7866（**差 2.1%**） |
| 逐名归组闭合 | 两帧都 **0.000 µs** |
| 多数模块的 ms | 32 个模块里 **22 个在 ±5% 内**（`fused_swin_core` 1.00×、`fused_dynamic_front` 1.01×、`_pairs` grid=(270,4) 1.00×、`_matmul` grid=(8,96,1) 1.01×、`fused_c32_projection` grid=(14690,3) 1.00×） |

### §6.2 不可复现的部分（硬）

| 模块 / grid | frame 30 | frame 31 | 比值 |
|---|---:|---:|---:|
| `window_layout_v1._unpack` grid=(58760,) | 145.94 µs | **2800.21 µs** | **19.19×** |
| 同上 grid=(57344,) | 140.21 µs | 2662.08 µs | 18.99× |
| `fast_matrices_v3._matmul` grid=(29380,1,1) | 1119.06 µs | 308.44 µs | 3.63× |
| `window_block_attention_v3._kernel`（整模块） | 6.0705 ms | 1.6529 ms | 3.67× |
| `fused_c32_mlp_lut_v1._kernel` grid=(14336,) | 558.75 µs | 1868.12 µs | 3.34× |
| `nr_backend.triton_math._tiled`（整模块，2 次） | 4.7960 ms | 1.6943 ms | 2.83× |

**grid 相同 ⇒ 工作量相同 ⇒ 差异不可能是"内容变了"。** 而且它在模块之间**互相抵消**：
frame 30 贵在 `window_block_attention_v3`(+4.4)、`_tiled`(+3.1)、`_matmul`(+1.6)；
frame 31 贵在 `_unpack`(−5.2)、`mlp_lut`(−2.0) —— 总量几乎不变。

⇒ **这不是数据相关的耗时差异，是重叠执行/队列级的时间归属不稳定**（剖析遍把 host 拖慢约 25×，
设备大量空转，单次 `dur` 里可能含等待）。**本轮只登记现象与量级，机制不下结论。**

### §6.3 由 §6 得出的引用规则

| 可以引用 | 不能引用 |
|---|---|
| **模块身份**（`_kernel` 是这 8 个） | 单帧的**名次**（第 3 名和第 7 名可以互换） |
| **启动次数**（逐帧逐项相同） | 单帧的**比值**（"占设备 14.3%" 这种） |
| 量级（1 ms 级 / 100 µs 级 / 10 µs 级） | 小数后两位的 ms |
| **µs/次 的量级**（4 µs / 45 µs / 300–960 µs 三档） | 同一模块内部的 µs/次 精确值 |

⚠️ 这一条**直接约束 §5 那张表**：`window_layout_v1._unpack` 的 14.3% 和第 2 名是**这一帧的**结果，
不是它的性质；`_matmul` 的 16.4% 才是稳的（两帧 8.0962 / 6.5028，且它的中位网格 1.00–1.01×）。

## §7 N6b §5.1 那个活矛盾的判决

N6b §5.1 测出：刀① 短路掉的 175 次 `_kernel` **只值 1.01 µs/次**，而 82 ms 时代的
`DEVICE_SPLIT_REPORT.md` 给 `triton_fp8._kernel` 的单价是 **8.23 µs/次**。报告列了两个可能、未下结论。

**两个可能同时成立，而且现在能算出来：**

* **① 成立**：`nr_backend.triton_fp8._kernel` 内部 grid 从 **1792 到 29380**（16 倍跨度）。
  小 grid 只要 **6–11 µs**、巨大 grid 要 **149–151 µs** ⇒ 被短路的 175 次是**小 grid 尾巴**。
* **② 成立**：合并名确实把 8 个模块算成一行 —— 但那**不是** `triton_fp8._kernel` 的问题，
  82 ms 那份报告用启动序 zip **本来就把它拆对了**（8.23 µs/次 ≈ 本轮 11–14 µs/次，同量级）。

**⇒ 定论**：引用 `quantize_fp8` 的设备成本必须同时带**次数**与**grid 分布**；
"383 次 × 8.23 µs" 这种外推**在现行产品上会高估**（现行 208 次 / 2.3–2.9 ms）。

## §10 边界

1. **诊断，不是证据跑**：不产出正确性产物、不参与任何门槛、不写 fastpath。绝对毫秒**不作加速比证据**。
2. **只剖析了 3 帧**（2 / 30 / 31）。§6 的双帧判据只能区分"稳/不稳"，**不能**给逐模块的置信区间。
3. **§6 的机制未定论** —— 只登记了现象（同 grid 差 19×、总量守恒、模块间抵消）与量级。
4. **归因口径强于 82 ms 那份表**（按真实被调用的 Python 函数，无 `src` 反查的 0.65% 歧义），
   但**同样受"调 用点不可分"的限制**：`pre_mlp.py:47` 把 `triton_fp8._kernel` 别名成 `fp8_kernel` 再启动，
   本轮把它归到 `nr_backend.triton_fp8`（**按定义模块**，这是内核身份的正确归属），
   所以**同一模块的不同调用点要靠 grid 区分**（本轮的 grid 表已提供）。
5. 产品源 0 改动；冻结缓存 0 改动；未占 GPU 以外的时间。
6. 事件里 **18 次 Memcpy** 归类为"非 `_ZTS` ⇒ triton 家族"只是**分类规则的产物**，与 Triton 无关；
   §3.1 已把它的量（0.0813 ms）单独登记，不混进任何模块。
