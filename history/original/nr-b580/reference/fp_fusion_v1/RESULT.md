## §2 方法：一把只翻一个布尔的刀 + 借来的设备尺子

| 件 | 来源 | 作用 |
|---|---|---|
| **设备尺子** | `l3_1_insitu_v1` 的剖析补丁串（`CallSiteNamer` + `summarise`，源码补丁 + exec） | 给出被剖析帧的**设备忙时**、**逐内核**设备时长（`gpu_kernels`）、启动顺序（`launch_order`）、`gpu_instances` |
| **刀（off/on）** | 本轮新写：在**最内层**包一层 `JITFunction.run` | `NR_FP_FUSION=off/on`；产品源码 0 改动 |

### 2.1 刀的形状：只翻「显式传了 `False`」的那一次启动

`enable_fp_fusion` 是**启动选项**（`kernel[grid](…, enable_fp_fusion=False)`），不是文件级全局。
刀**不做**任何算法/结构改动（不动数据流、不动调用点、不动分块、不动精度），只做一件事：

```python
def run_with_fusion(inner, *args, **kwargs):
    if kwargs.get('enable_fp_fusion') is False:
        kwargs['enable_fp_fusion'] = True          # ← 唯一的改动
        STATE['flipped'] += 1
        STATE['flipped_kernels'].add(inner.fn.__module__ + '.' + inner.fn.__name__)
    return original(inner, *args, **kwargs)
```

⇒ **被碰到的集合完全由产品源码决定**，不由我们挑选 ⇒ 可归因、可复算。
两臂共用同一份产品源码，**唯一差别是这一个布尔**。

### 2.2 为什么这个缝安全（不遮蔽 namer）

`dense_ab_v1` 的 `CallSiteNamer` 包的是**同一个** `JITFunction.run`，且**不绕过** `run` **本身**
（`dense_ab_entry_v1.py:69`，且有 zip 的 C6 自检背书）。
本刀在它**之前**安装、成为**最内层**包装 ⇒ **namer 记录在内、刀翻转在外**，互不遮蔽。
判据 P3 验证了这一点：namer 总启动数两臂 **Δ = 0.0**，`gpu_instances` 两臂均 **1432**。

### 2.3 缓存：翻选项 = 换编译键 ⇒ ON 臂必须重编

选项是**编译期参数**，Triton 的缓存键把它算进去
（`runtime/compiler.py:255` `key = get_cache_key(src, backend, options, env_vars=…)`），
且 Intel 后端真的把它喂给 LLVM：`intel/compiler.py:461` `intel.set_fast_math(llvm_mod, metadata['enable_fp_fusion'])`。
⇒ ON 臂**确实重新编译**，不会因缓存命中而假阴性。

因此臂序里保留一个**预热编译臂** `00-warm-on`（`--allow-compile`, limit=2）把新变体落进**缓存副本**；
四个计量臂全部 `allow_compile=False` 走 DiskOnly。
冻结缓存**一个字节都不动**（只用副本 `D:/fp-fusion-v1/cache`）。

## §5 主结果 2：归因分裂（被翻的 / 没被翻的）

本轮**启动次数一个都不变**（只换编译选项）⇒ 不能按「启动次数是否改变」切 C/D
（那是 `a_insitu_v1` 的切法）。改用「**这一次启动有没有被翻**」切：恒等式 `Δ_busy ≡ Δ_C + Δ_D`，
残差 **0.000000 ms**。

| 集合 | 内核类数 | Δ 设备时长 | 说明 |
|---|---:|---:|---|
| **C 被翻内核所在的类** | 18 | **+0.3531 ms** | 覆盖 off 臂 31.5929 ms/帧（Triton 的 **98.2%**） |
| **D 其余** | 54 | +0.0099 ms | 合计比值 **1.00185**（几乎不漂） |
| **合计** | 72 | **+0.3630 ms** | = Δ_busy（闭合自检通过） |

### 5.1 ⚠️ 切法口径（必须随结论一起读）

profiler 的 `gpu_kernels` **只按裸内核名聚合**：`_kernel` 一个名字就吃下
**299.0 次/帧、13.6220 ms**，把 `fused_c32_*` / `fused_swin_*` / `nr_backend.triton_fp8` /
`window_block_attention_v3` 等**多个模块混在一起** ⇒ **拿不到逐模块的设备 ms**。
所以 C/D 只能按「裸名里有没有被翻的模块」切，C 集因此覆盖 Triton 的 **98.2%**。

**它不能隔离「被翻内核的净贡献」。** 它能支撑的是一条**弱但干净的**结论：

> D 集（54 个未被翻的类，`Δ_D = +0.0099 ms`，比值 1.00185）几乎不漂
> ⇒ **这 +0.3630 ms 落在被翻内核所在的整类里，不是量测漂移。**

### 5.2 方向一致性（比量级更强的一条）

* off 两臂均值：37.1162 / 36.7944 → 合并 **36.9553** ms
* on 两臂均值：37.3503 / 37.2863 → 合并 **37.3183** ms
* 4 个跨臂对 Δ(on−off)：**[+0.2342, +0.1702, +0.5559, +0.4919] ms** ⇒ **4/4 为正（on 更慢）**
* 帧级 Welch t = **2.36**，正态近似双尾 **p ≈ 0.018**（n=6 vs 6）

⚠️ 但真正的不确定度以 **P4 的臂级重复差 0.3217 ms** 为准 —— 它与效应同量级。
⇒ 只能说「**量级上分辨不出、方向上一律偏慢**」，不能说「显著变慢」。
**无论哪种读法，② 都没有省时间** —— 这正是判决要问的那一件事。

## §9 边界（诚实清单）

1. **只 12 帧窗口、3 剖析帧/臂、一段素材**（480×864）。设备读数由源码决定，但本轮只报「这一段」。
2. **设备读数不回答帧墙传导率、不回答 fps。** 本轮不越界。
3. **C/D 切法不能逐模块隔离效应**（§5.1）：`_kernel` 是 299 次/帧的聚合名 ⇒ C 集覆盖 98.2% 的 Triton。
   本轮只能给「被翻内核所在的整类」的 Δ，外加一条**干净的漂移上界**（D 集 +0.0099 ms）。
4. **P4 的 off 臂偏松（0.3217 ms），原因未查明。** 候选：off 帧更长（≈37.0 ms vs on ≈37.3 ms），
   整机时钟/功耗状态不同；或 profiler 附着期的会话内漂移。已把它**当不确定度使用**，不写成结论。
5. **效应量级 = 1.10× 不确定度** ⇒ 本轮**不能**声称「显著更慢」，只能声称「**没有省时间**」+
   「方向 4/4 一致偏慢」。
6. **本轮未做人工看片**，也没跑 LPIPS / 容差门。数值差见 §7，**是否可接受需 D5 第 3 项裁定**。
7. **fail-fast**：剖析遍在解释器**拆卸期**触发 Windows fail-fast（0xC0000409 / 0xC0000005），
