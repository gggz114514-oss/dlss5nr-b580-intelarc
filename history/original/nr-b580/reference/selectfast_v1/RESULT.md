**日期**：2026-09-17
**对象**：`nr-b580-int8` 的快速路径（`c512_arith=int8`，480×864，243 帧冻结素材）。
**目录**：`selectfast_v1/`（协议要求「新改动必须另起一轮目录」）。

## 1. 一句话

诊断文档把这一层记为「缓存 `select`，名义 ≤ **2.85 ms**，不动字节」（`FRAME_BUDGET_REPORT.md` §8.2 第 3 行）。
**实测：独立收益 1.041 ms；叠在第一层之上只剩 0.647 ms。**

而且——**这一层真正的产出不是那 0.647 ms，是它证伪了报告里的一句话。**
§8.3 断言「第 2、3 行是**独立的** host 工作，**可以相加**（10.69 ms）」。2×2 实测：

```
层4 独立        = 1.041 ms
层4 在层1 之上  = 0.647 ms      ⇒ 37.9% 的收益已经被第一层吃掉
```

**⇒ 第 2、3 行不能相加。** 报告里那句「两者是独立的 host 工作」是错的。

## 2. 为什么必须做 2×2，而不是简单的 off/on

`select` 内部就是一次 `jit.warmup`：

```python
def select(jit,configs,args_for,grid_for,**options):     # spill_preflight_v1.py，全文 18 行
    for config in configs:
        args=args_for(config);grid=grid_for(config)
        kernel=jit.warmup(*args,grid=grid,**options)     # ← 走 JITFunction.run
        kernel._init_handles()
        ...
```

而第一层 `hostfast` 替换的正是 `JITFunction.run`（`hostfast_cuts_v1.py:161`），
且 `_run` **显式处理 `warmup=True`**（`hostfast_cuts_v1.py:261-262`）：

```python
if warmup:
    stats['warmup'] += 1
else:
    stats['launch'] += 1
```

⇒ 两层作用在**同一段代码**上。只做 `off` / `on` 两臂，量到的是**第四层的独立收益**
（在一个第一层不存在的地基上），不是「在第一层之上还剩多少」——
而后者才是决策要的数。所以四臂：

| tag | `HOSTFAST_CUTS` | `SELECTFAST_CUTS` |
|---|---|---|
| `off` | off | off |
| `l4` | off | select |
| `l1` | run,getitem | off |
| `l1l4` | run,getitem | select |

因子对照由汇总脚本自己算（`selectfast_ab_summary_v1.py`），不让读者从加速比表里心算。

### 2.1 跑前的两种对立假设（先说清楚，免得事后挑对自己有利的解释）

- **H1**：§7 的四分区是**排他**的（四项之和 = 帧墙），所以 `select` 的 2.83 ms
  **不含**它内部嵌套的 `run` ⇒ 层1 动不了它 ⇒ 层4 之上也应接近 2.8 ms。
- **H2**：`warmup` 调用本身的开销记在 `select` 行里，层1 已经把它变成查表
  ⇒ 层4 之上应接近 0。

**实测站 H2 这一侧，但不是 0 —— 是 0.647 ms。** 两个假设都不完全对，
这正是「必须测」的理由。

## 4. 字节门：这一层为什么不可能改字节

缓存返回的是**同一个 `(config, kernel, selection)` 三元组**，
内核对象的同一性由运行期抽样自检保证（见 §6），所以下游拿到的
config / kernel / 资源元数据逐位相同 ⇒ 启动的内核与参数完全一致。

逐帧字节门把这个论证变成可测的事实：**8 轮 × 243 帧全部逐字节相等。**

## 6. 自检：这一层的正确性判据

### 6.1 运行期抽样自检（`verify_fail == 0` 才算通过）

每 32 次命中，用**真路径**重算一次 `select`，比对**内核身份**（`is`）。
不一致 ⇒ 退役该条目 + 计数 + 打印 + 返回真路径的结果。

实测：`l4` 与 `l1l4` 各 **2868 次自检，全部通过，0 失败**。

### 6.2 离线自检（不占 GPU）—— 本轮固化下来的新东西

`selectfast_selftest_v1.py`：注入一个**忠实模拟**的假 `spill_preflight_v1`
（同一组实参返回**同一个内核对象**，模拟 Triton 的编译缓存），测三件事：

| 用例 | 判据 | 实测 |
|---|---|---|
| 键与帧无关 | 逐帧 `torch.empty` 新张量仍命中；缓存条目数**不随帧增长** | 160 次调用，命中 158，条目 **2**，自检 4 次失败 0 |
| 自检非空转 | 把假模块改成「每次返回新对象」⇒ `verify_fail` 必须 > 0 | 自检 4 次，**失败 4 次** ✓ |
| 命中率过低会旁路 | 键每次都变 ⇒ 触发旁路 + 清空条目 + 后续回落 | 1200 次调用，命中 0，旁路 2，回落 176，条目 **0** |

**它当场抓到一个真 bug**（§7.2），代价 0 GPU 秒。

### 6.3 一条不变量：与改动无关的计数在两侧完全相等

| 计数 | `l1` 臂 | `l1l4` 臂 |
|---|---:|---:|
| 第一层 `launch` 命中 | 461434 | **461434** |
| 第一层 未命中 | 828 | **828** |
| 第一层 回落 | 0 | **0** |
| 第四层 `select` 调用 | 0（未装） | 91854 |

启动计数逐位相同 —— 第四层只动了 `select`，没碰任何一次内核启动。
**这是「两层各管一段、没有互相污染」的直接证据。**

## 7. 本轮修掉的真实错误（两条都是我自己引入的）

### 7.1 `'%s' % (元组)` 会被展开成参数列表

```python
print('[selectfast] 第一层 hostfast: %s' % (cuts.cuts if cuts is not None else 'off'))
# cuts.cuts 是 ('run','getitem') ⇒ TypeError: not all arguments converted during string formatting
```

**probe 在 10 秒内就把它拦住了**（第二臂 `rc=1`），没让 8 轮正式跑白占一次租约。
这正是「`probe && ab` 且 probe 的 rc 必须传出去」这条设计的价值 ——
第三层初版把 probe 写成永远成功，于是冒烟测试完全没起到闸门作用。

### 7.2 抽样自检的触发条件写错，短跑里根本不跑

初版按「**单个键**攒够 `sample=32` 次命中」触发。而 probe 只有 3 个稳态帧，
调用数摊到 13 个 jit、38 个键上，每个键都攒不到 32 次 ⇒ `verify=0`
⇒ 闸门会判「自检一次都没跑」。**根因是触发条件写错，不是刀坏了** ——
但报告里会看起来像刀坏了。

改成**全局命中计数**取模：短跑也一定会验到（probe 实测 22 次），
长跑的自检开销仍可忽略（1/32 的真路径，且真路径本身已被缓存）。

**这个 bug 是离线自检抓到的，代价 0 GPU 秒。**

### 7.3 一次虚惊：两轮的中位帧墙逐位相同

我的 `0-off` 中位帧墙 `83.90520000102697` 与第一层那轮的 `0-off` **逐位相同**，
第一反应是「读到了陈旧产物」。逐条查过，**不是**：

| 检查 | 结果 |
|---|---|
| 原始文件 sha256 | **不同**（`e7d02fda…` vs `ba5b05ab…`） |
| `mean` / `min` / `max` | 全部不同 |
| 帧墙量化步长 | **0.1 µs**（最大偏差 0.0000 个量化步） |
| 两轮 239 个帧墙值的重合度 | **4 个（1.7%）** ⇒ 测量是真实独立的 |
| 中位附近的局部密度 | 40–80 值/ms ⇒ 撞同一格点概率约 1/150 |

⇒ **是约 1–2% 概率的巧合，不是产物复用。**
0.647 ms 的差异 = **6470 个量化步**，量化完全不构成分辨率问题。

## 8. 机制：那 0.647 ms 是怎么来的（可对账）

第一层的 `warmup` 命中数在两臂之间差了一个**精确的量**：

| 臂 | 第一层 `warmup` 命中 | 第四层 `select` 调用 | 说明 |
|---|---:|---:|---|
| `l1` | **91778** | 91854 | 每次 `select` 都走到 `warmup` ⇒ 都是第一层的查表命中 |
| `l1l4` | **2868** | 91854 | 只剩第四层自检那 2868 次真路径会走 `warmup` |

**⇒ 第四层消灭了 91778 − 2868 = 88910 次第一层的 `warmup` 查表命中**
（486 帧 ⇒ **183 次/帧**）。

反推每次被消灭的查表命中的净值：

```
0.647 ms ÷ 183 次/帧 ≈ 3.5 µs/次
```

即「第一层一次 `warmup` 查表命中」≈ 3.5 µs（键构造要遍历 13 个实参 + 字典查找）。
**第四层用自己的一次键查找替掉了它，净赚 3.5 µs/次。**

而第四层的**独立**收益 1.041 ms ÷ 189 次/帧 ≈ **5.5 µs/次** ——
那是「`select` 函数体整段」减去「第四层自己的键构造成本」。

**⇒ 两笔账都落在同量级，且方向一致：这一层省的是「`select` 那 18 行 Python」，
不是它内部的内核查表。**

## 10. 这一轮能证明什么 / 不能证明什么

### 能证明

1. **第四层的收益是 0.647 ms（在层1 之上），不是 2.85 ms。** 8 轮 ABBA、
   四臂极差 0.04%–0.27%，字节门 8×243/243。
2. **§8.3 的「第 2、3 行可以相加」是错的。** 37.9% 的重叠是实测的，机制也查清了
   （第四层消灭了 183 次/帧的第一层 `warmup` 查表命中）。
3. **`select` 是 189.00 次/帧，摊在 13 个 jit 上**，其中 72 次/帧（38%）
   来自 grep 找不到的 `window_block_attention_v3`。
4. **不改字节**：返回同一个 `(config, kernel, selection)` 三元组，
   内核身份由 2868 次抽样自检保证（0 失败），并由 8×243 帧字节门实测确认。
5. **一条不变量**：两臂的 `launch` 命中 461434 逐位相同 —— 两层互不污染。

### 不能证明

1. **`l4` 与 `l1l4` 两臂的第四层计数逐位相同**，所以「层4 自身行为不受层1 影响」
   只是**观测到的**，没有独立论证 —— 但它是一个可预期的性质（两者作用对象不重叠）。
2. **0.647 ms 只比四臂极差（0.03–0.23 ms）大 2–3 倍**，是本轮最弱的一个数。
   它的方向可信（ABBA 对称 + 机制可对账），但量值有 ±0.2 ms 量级的不确定度。
3. **`l1` 臂 81.84 ms 与 `merge_v1` 的 `host` 臂 81.54 ms 相差 0.3 ms** ——
   两个不同轮次、不同入口的同构臂给出同一量级，是交叉验证，但没到逐位一致。
4. **层3（`warpsync`）未与层1/层2 合并实测**，所以 71.88 与 71.23 都是外推。
5. **§7 的 2.83 ms 是 Phase 0b 仪器口径**，与干净跑的 1.041 ms 不可直接比 ——
   仪器本身会给 Python 密集的代码加重。这也是「名义值 ÷ 3~4」这条规律的来源之一。
