# RE8 游戏快速链：算术与内部搬运的测量边界

本轮对象是现役 360p／480p／540p 原尺寸快速链；不使用 NR256 的结果推断游戏后端。本文先整理已有 540p 稳态画像，后续候选的 3 档实测应在同一口径下追加。没有把 AMD／NVIDIA 的内部时间当成本机测量值。

## 已经能够确定的部分

960×540 输入的离线图重放测试中，桥接输入和输出分别约 0.25／0.29 ms，模型段约 54 ms；这些是不同配对轮次的量级判断，不能跨轮相减成精确比例。见 [既有边界审计](COMPUTE_VS_TRANSFER_20260925.md)。

已有 VTune 采样的后段 14–18 秒窗口，按 GPU **任务累计时长**重算，显式 Level Zero 内存拷贝为 0.023692／2.478367 秒，约 **0.96%**。这个比例不能解释成“整帧只有 0.96% 在搬运”：核内加载和存储、中间张量物化、布局重排、填充、量化、寄存器溢出均可能记在 Compute 类。任务可以重叠，累计时间也不是帧墙钟。见 [稳态时间窗](STEADY_GRAPH_COPY_20260925.md)。

使用修正分类的 [`summarize_vtune_tasks.py`](../tools/summarize_vtune_tasks.py) 对同一稳态报表重新列账：通用 `_kernel` 约占任务累计时长 39.85%，名称匹配到 `_pairs/_project/_tiled` 等**融合混合核家族**约 20.10%，名字含 dot/matmul 的**矩阵混合核**约 18.17%，已命名的打包与量化约 5.88%，拷贝／填充核约 4.51%，纯显式拷贝约 0.96%；其余包含逐元素和未归类任务。同名核可能来自多个模块，尚不能逐一溯源。此表只能说明值得追踪的任务分布，**没有**分离混合核内的 XMX 算术时间与数据加载时间。原始分类结果位于 `D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/steady-classes-v2.json`。

更细的离线工具 [`analyze_vtune_task_traffic.py`](../tools/analyze_vtune_task_traffic.py) 对同一 TSV 逐行重列账，未能从名称可靠分类的任务仍占累计时长 **45.96%**，其中通用 `_kernel` 一项为 987.709 ms。其带宽乘任务时间仅是采样**代理值**，不是实测物理字节或严格上界；连显式拷贝的 `Transfer Size` 6.768 GB 与该代理值 2.688 GB 都不一致，证明两种计数口径不能混用。完整表在 [D 盘离线诊断](</D:/Codex-NR-Experiments/nr-b580/re8-compute-movement-offline-20260927/vtune_task_traffic.md>)。两套分类规则不同，不应把各自百分比互相相加。

另一个已识别的实体开销是 post 的非连续视图在 `_tiled_dot` 前被物化；三档逻辑复制量约 18／28／40 MiB。这些字节未包含在单独 `_tiled` 核的 GPU 任务计时内。局部 stride 直读候选及完整帧结果见 [三档融合实验](GAME_THREE_MODE_FUSIONS_RESULT_20260927.md)，它是消掉一个边界后净收益的证据，而非原复制操作的独立耗时。

## 下一轮如何区分

1. **先给每个连续段列职责和字节账。** 捕获期记录实际矩阵 M/N/K、精度与 provider，以及前后张量的形状、stride、dtype 和是否真正物化。`view` 不算物理复制；`contiguous/copy_` 需确认是否产生任务。`numel×itemsize` 仅是逻辑数据量，不当作实测 DRAM 字节。
2. **稳态做 GPU 画像。** 在真正图重放帧前后放同队列标记，映射编译核和 VTune 任务，分别报告矩阵混合核、逐元素/量化核、布局/填充核、显式拷贝和无法归类的融合核。另收集可用的 DRAM/L3/SLM 带宽、XMX 活跃、占用、GRF 与 spill。若存在多队列，关联事件依赖并报告 GPU 区间并集，不能把一条队列以外的任务忽略。
3. **用单边界配对实验估计净收益。** 保持当前精度和历史语义，分别删一次中间物化、改一次生产者输出布局或融合一次量化；同输入、同图状态做 B-C-C-B 完整帧。差值是这项改动在当前硬件的**净收益**，可能包含缓存和占用变化，不能宣称为原操作的纯搬运毫秒数。再用独立的局部核实验和硬件带宽计数解释差值。
4. **真实连续帧单独验数值。** 三档使用相同 960×540 视频和非零运动向量，首帧重置，后续连续历史；正确性轮逐帧比对。计时轮不逐帧回读，预热与编译另计。只有无分析器的完整帧配对能决定是否晋升候选。

因此，当前已经可以排除“桥接显式拷贝占几十毫秒”，但仍**无法可靠给出模型图内纯计算／搬运各占多少毫秒**。最有价值的下一步是把通用 `_kernel` 与融合核映射到现役 360/480/540 的实际生产者—消费者边界，并通过有界改写验证每一处收益。
