# RE8 540p 模型图内归因：继续细化的边界

**目标仅为 RE8 当前 540p 原尺寸快速后端，不优化 NR256。** 现有稳态整链约 55.5 ms，其中模型段约 54.4 ms。此前 eager 逐组同步结果仅可粗排 ViT、post、pre，不能折算成生产图重放的组耗时；详见 `COMPUTE_VS_TRANSFER_20260925.md`。

## 图内时间事件：不适用

隔离探针 `tools/probe_graph_events.py` 在便携版相同的 XPU/PyTorch 环境中，用两个张量算子及三个 `torch.xpu.Event(enable_timing=True)` 捕获一张小图。捕获与重放执行到查询阶段，但首次 `elapsed_time` 报错：`Profiling information is unavailable for events returned from a submission to a queue in the recording state.` 原始记录：`D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/event-support.json`。本探针没有完成数值比较，因此只证明此计时 API 在当前录制队列不可用，不证明模型图有问题。

## 对已有 VTune 稳态窗口的进一步分类

从现有 VTune 结果对请求的 14–18 秒窗口重新导出的完整任务表：`D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/steady-computing-task-14-18.tsv`。采集实际在 17.614 秒结束，因此该窗口只有约 3.614 秒。`tools/summarize_vtune_tasks.py` 的可复算输出在同目录 `steady-task-classification.json`。任务累计时长合计 2.478367 秒。这不是墙钟的占比，也不应直接除以游戏帧数；GPU 引擎任务可能并行，VTune 还会干扰执行。数据库显示该窗口 65,871 个任务全部在同一个 GPU 队列，但仅凭队列不能分清模型与桥任务。

| 仅按可识别名称的类别 | 累计秒 | 任务累计占比 | 边界 |
|---|---:|---:|---|
| 通用 `_kernel` | 0.987709 | 39.853% | 无法辨认算术、布局、量化或拷贝 |
| 已由源码定位的算术核 `_pairs`、`_project`、`_tiled` | 0.498190 | 20.102% | 分别含 cubic MLP、投影和分组点积；混合数值与读写 |
| 名称明确的矩阵核 | 0.450257 | 18.167% | 只是矩阵计算的可识别下界 |
| 其他无法稳定归类的名称 | 0.261073 | 10.534% | 仍需图内分段或源码映射 |
| 名称明确的打包／量化核 | 0.145670 | 5.878% | 有数值处理，非纯拷贝 |
| 名称明确的复制／填充核 | 0.111776 | 4.510% | 设备计算核内完成，不是显式传输任务 |
| 显式 `zeCommandListAppendMemoryCopy` | 0.023692 | 0.956% | VTune 任务类型；地址来源仍不明 |

因此，**显式传输任务不是主要耗时**。源码可识别的矩阵与上述数值核至少占累计 GPU 任务时长 **38.3%**，但这仍不能直接回答“算术还是数据重排主导”：约 **50.4%** 留在通用 `_kernel` 与其他未归类名称里。把全部 `Compute` 类任务说成矩阵乘，或把复制／量化核统称为传输，都会高估对应项。

该次 VTune 汇总还报告 XVE 在 GPU 忙时有 65.4% 的时间处于 stalled/idle，峰值占用率为 62.7%（同目录 `vtune-summary.txt`）。这说明实际执行效率仍有空间，但该全局指标不区分访存等待、算子依赖、调度和指令利用率；不能据此声称 GPU DRAM 搬运主导，也不能直接推算融合收益。

进一步查源后，`_pairs`（0.236 秒）可来自原生 cubic MLP 的成对展开计算，`_project`（0.143 秒）既可来自 FFN 投影也可来自窗口投影，`_tiled`（0.119 秒）是分组半精度点积。这些核包含真正的数值计算，不能把上表 `other` 行等同于内存搬运。反过来，`_kernel`（0.988 秒）在项目里同时被 FP8 量化、注意力、前处理、融合 MLP 等不同模块复用，不能按名称分摊给任何一段。该窗口共 65,871 个 GPU 任务，包括 `_kernel` 22,030 次、`_matmul` 5,717 次、显式拷贝 2,826 次。这支持继续核查**图重放内部的小核与依赖链开销**，但任务数本身不能换算出可节省毫秒，也不能把该窗口的任务总数当作单帧任务数。

同名 `_kernel` 仍可按 VTune 任务类型和启动网格区分。例如该窗口类型 4（网格 `1310720 x 3`）46 次累计 56.384 ms，类型 224（`1337472 x 3`）47 次累计 55.061 ms，类型 51（`655360`）1,209 次累计 84.161 ms。前两种约每帧出现一次，第三种出现多次；类型编号只在本次采集内有效。这些类型目前没有可靠的模块标签，待图内标记归位后再讨论它们是在做算术还是格式／布局处理。

此前的图 I/O 审计还数出 **41.86 MB/帧已知显式图输入／输出复制**，见 `D:/Codex-NR-Experiments/nr-b580/re8-graph-io-audit-20260925/graph-io-byte-only.json`。它没有覆盖模型内部读写、隐式流量、几何与桥，也没有给这些字节单独计时；字节数大不能直接推断它们主导 54 ms 模型段。

下一层在整张 540p 原尺寸图里加入可识别的阶段标记，用设备时间线划分 pre、编码、ViT、解码和 post。标记包住模型主体；图静态输入复制发生在第一个标记之前，池外输出复制发生在最后一个标记之后，故分段之和不等于完整模型段。测试图和生产图须对照输出 SHA-256、整体帧耗时及标记开销。不能仅凭源码中存在 `repeat_interleave` 就断言 post 是最大瓶颈。

## 生产源码里的 post 候选，尚未确认耗时

便携运行时 `nr_backend/post.py` 的 `forward_head` 先将 HWC32 特征沿两轴各扩展 2 倍，在较大的画布上做注意力和投影，最后 `forward` 才截取 RGB 所需区域。540p 档的活动模型图像为 544×960，内部 skip 画布为 640×1024；最终 RGB 仅使用 522,240／655,360 像素，即 79.7%。粗特征约为 320×512×32 个 half 元素，第一次沿高扩展写出约 20.97 MB，第二次沿宽扩展写出约 41.94 MB。这里的字节是源代码层面的**逻辑输出量**，不是实测显存流量或耗时。

产品树里的 `post_region_scope_v1.PostRegion` 只在 RGB、特征、skip 分别为 256×256、160×160、320×320 时启用；540p 原尺寸不满足条件。只借鉴其“保留完整 8×8 注意力窗口，只裁最终输出依赖区域”的**算法原则**，需要在 540p 原尺寸上重新实现、验字节并测整帧。NR256 本身不列入工作范围；540p 的收益上界首先受 post 自身的图内耗时限制，也不能借用旧实验的百分比。

## 分析器兼容性

`tools/probe_graph_markers.py` 的最小图包含前后两个具名 Triton 标记核。它的四次重放数值与无标记的张量表达式完全一致，最终标记值为 22；但当前 PyTorch XPU profiler trace 仅见 Level Zero 提交／同步事件，未见图内 GPU 核名。原始记录为 `D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/marker-support.json` 和同目录 `marker-trace.json`。此次启用 PyTorch profiler 的 Python 进程在保存报告后，退出阶段的 `ze_tracing_layer.dll`／`pti.dll` 报错并异常退出；数值结论仅依赖已持久化的报告和 trace。

随后小图 VTune GPU hotspots 验证成功：`D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/vtune-marker-small/sqlite-db/dicer.db` 含 68 组按顺序完整的前后标记；丢弃 4 组预热后，64 组标记之间各有一个加法任务，中位间隔约 0.00427 ms。`tools/extract_vtune_graph_stages.py` 从每个 GPU 任务的时间戳抽取区间，按标记所在 GPU 队列筛选任务，并保留任务类型及启动网格以区分同名 `_kernel`；`marker-mini-intervals-v2.json` 保存可复算结果。VTune 提示部分 GPU 调度时间戳可能不可靠；该小图只验证方法可行，不代表完整 NR 图的任何性能收益。下一步在隔离的 540p 原尺寸图上验证顺序、输出哈希与标记开销，再决定是否把最慢段继续切细。

## 540p 原尺寸整图首轮分段

隔离标记只写一个与模型张量分离的整数元素，按生产 `capture_body_v1.forward_front` 的调用顺序放置 14 个边界。`D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/full-540/marked-smoke.json` 验证 4/4 计时帧实际图重放，两个重置输出的 SHA-256 均为冻结值 `d20483f7d3517cf74a83e99d3a06182972194ee06396d83a569deed4ae64f98d`。14 个标记仅在 D: 的隔离缓存预编译，G: 原运行时缓存文件列表前后相同。

同目录 `vtune-marked/sqlite-db/dicer.db` 有 31 组完整标记序列、0 组缺失或乱序。按脚本调用次序排除前 21 组预热／捕获以及末 2 组输出哈希后，8 个稳态序列都在同一 GPU 队列，跨阶段延续执行的任务数为 0；每段可复算统计在 `stage-intervals-steady.json`。8 次主体标记跨度的中位数为 **50.775 ms**，范围 50.446–51.325 ms；跨度减各阶段区间之和的中位数约 **0.0175 ms**，只描述图内标记核和间隙，不是完整测试开销。该跨度不含图输入复制、图输出复制、桥和几何。

**这是候选位置排序，不是生产耗时或可节省毫秒。** 本次原始预检见到 DWM/Codex 背景 GPU 活动，两个运行报告均标记 `valid_for_performance=false`；VTune 下整链中位数约 65.69 ms，与无 VTune 基线 55.5 ms 不可横比。插入标记本身的整帧开销也尚未配对测量。8 帧内各段时间波动较小且顺序稳定，足以提出优先继续切细 post 与 pre 的诊断假设。此前 eager 同步把 ViT 排首位，生产图的这轮采集却显示 ViT 约 2.83 ms，证明不能据 eager 排名直接选优化目标。

## 540p post 二层分段

`D:/Codex-NR-Experiments/nr-b580/re8-graph-event-probe-20260925/post-540/marked-post-smoke.json` 和 `marked-post-vtune-run.json` 分别有 4/4、8/8 图重放，重复重置输出仍是上面的冻结 SHA-256。D: 存放所有标记核，G: 运行时缓存的文件数 18,596，前后无新增或删除。VTune 库 `vtune-post-540-marked/sqlite-db/dicer.db` 有 31 组完整的 `nr_post_00..07` 标记，顺序正确；排除前 21 组和末 2 组后，8 次稳态都在同一 GPU 队列。完整序列和任务类别在 `post-intervals-steady.json`。

| post 内部步骤 | 标记区间中位数 (ms) | 每次 GPU 任务数中位数 | 主要任务 |
|---|---:|---:|---|
| 注意力（含 MLP 输出量化） | 2.501 | 4 | 两个大型通用 Triton 核分别约 1.17、0.96 ms/帧 |
| RGB 头点积 | 1.709 | 2 | `_tiled` 数值核约 1.60 ms/帧 |
| 输出投影 | 0.869 | 3 | 矩阵核约 0.43 ms/帧 |
| 合并与填充 | 0.846 | 4 | 半精度融合乘加与填充 |
| MLP | 0.795 | 1 | 一个通用 Triton 核 |
| RGB／历史混合与存储 | 0.572 | 28 | 多个短逐元素核 |
| 特征扩展 | 0.498 | 4 | 逐元素与复制类核 |

post 主体标记跨度中位数 **8.180 ms**，与首轮 7.940 ms 属于不同采集，不能把差值当作插桩开销或回归。两轮原始预检都有桌面 GPU 活动，均标记性能计时无效；这里只用稳态内部结构及阶段排序筛候选。注意力和 RGB 头点积合计约占该轮 post 标记区间的一半，优先级高于单独优化 `repeat_interleave`。头点积在完整 640×1024 skip 画布上产生 8 通道，但 `ResetPostBlock.forward` 只读取 RGB 三通道和历史混合系数一通道，且最终只用 540×960 区域；可在隔离快速分支试验**保留完全相同点积顺序，只计算所需 4 通道及空间区域**，先做逐字节对照。裁剪点必须在 post 注意力及其依赖窗口之后，不能提前裁掉输入；视图变为非连续张量可能额外复制，需计完整链路，不能按像素比例宣称收益。这个候选与 NR256 无关。
