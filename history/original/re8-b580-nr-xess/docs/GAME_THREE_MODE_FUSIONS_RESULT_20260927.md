# 三档游戏快速链结构候选实测（2026-09-27）

对象是 **当前 G 盘 RE8 便携运行时**的 360p／480p／540p 原尺寸快速 NR 链。E 盘候选通过隔离上下文安装于每次新建的测试会话；G 盘游戏文件、默认执行链和缓存均未改动。所有候选使用同一 960×540 合成画面、非零运动、默认控制参数、融合历史采样及各自重新捕获的图；大缓存和原始计时只在 D 盘。这里的毫秒数是离线 `modes.process`，不是游戏帧率。

## 已验证的结果

| 候选 / 档位 | 基线中位数 | 候选中位数 | 差值 | 两组配对 | 字节门 |
|---|---:|---:|---:|---|---|
| 输出端直读＋可见范围＋4通道 / 360p | 26.922 ms | 26.625 ms | **−0.297 ms（−1.10%）** | 两组均快 | 三帧连续整链相同 |
| 同上 / 480p | 38.442 ms | 38.131 ms | **−0.311 ms（−0.81%）** | 两组均快 | 三帧连续整链相同 |
| 同上 / 540p | 53.476 ms | 52.816 ms | **−0.661 ms（−1.24%）** | 两组均快 | 三帧连续整链相同 |
| C32 七块＋上述输出端 / 360p | 27.109 ms | 26.225 ms | **−0.884 ms（−3.26%）** | −0.883／−0.876 ms | 480 个计时帧逐帧相同 |
| 同上 / 480p | 38.694 ms | 37.342 ms | **−1.352 ms（−3.49%）** | −1.368／−1.337 ms | 480 个计时帧逐帧相同 |
| 同上 / 540p | 53.564 ms | 51.323 ms | **−2.241 ms（−4.18%）** | −2.321／−2.142 ms | 480 个计时帧逐帧相同 |

每个配对为 B-C-C-B 顺序中的一组，每段 16 帧预热、输出端单项 80 帧／段、组合 120 帧／段；完整链计时均在每帧 XPU 同步后结束，哈希读回在计时之外。组合测试的 360/480/540 候选与基线对每个对应帧 RGB SHA-256 相同，所有计时帧均走图重放。编译仅发生在事前的 D 盘预编译测试；配对计时使用 `DiskOnly`。

输出端 [`post_k8_strided_v1.py`](../game/post_k8_strided_v1.py) 保留现有共享指数／整数累加和 FP16 舍入，从非连续的 post 投影裁剪视图直接读取，最终 32→8 头只计算模型入口范围及被 RGB/历史消费的前四个通道；上游窗口注意力和边缘上下文不裁。540p 的两个单独消融进一步表明两种改动均有收益：仅直读、仍算全内部画布 8 通道，配对中位数快 **0.310 ms**；直读并裁到模型入口、仍算 8 通道，快 **0.554 ms**；三项合并时快 **0.661 ms**。这些来自不同配对轮次，只能确认各配置相对同期基线的方向，不能把轮次间差值当成精确的单项成本。

C32 [`c32_repeated_tail_fusion_v1.py`](../game/c32_repeated_tail_fusion_v1.py) 把七个普通 C32 编解码块的注意力输出、投影、残差和裁边合成现有已验证的窗口尾段；这次把候选形状从 540p 扩到 360p、480p。每档七块的局部 skip/down 字节门，以及三帧重置→历史图重放整链字节门都通过，之后才运行上表组合计时。组合收益不能直接拆成两项之和；顺序、GPU 状态和候选相互作用均可能影响绝对毫秒。

组合候选仍是**隔离实验**。540p 组合 CV 从 1.25% 升到 1.54%，360p 从 1.25% 升到 1.36%；两档 P95 和两组中位数均改善。480p CV 从 2.15% 降到 1.13%。因此可以确认配对中位数和逐帧输出，却不能说所有波动指标均改善。部署前还需在安装包里预编译三档内核，用新进程 DiskOnly 检查、实机长时间切档/图重建与控制变化回归。

## Astra 指定的 AMD 式 C64 边界试验

[`c64_qkv_direct_pack_v1.py`](../game/c64_qkv_direct_pack_v1.py) 只替换编码器第二个 C64 块（block 6）的 QKV 中间写读：一个核在现有 FP16 XMX 累加和 FP16 写出舍入后，按现有归一化、FP8 舍入及窗口顺序直接写 Q/K/V，后面的 attention 与投影不动。三档局部 Q/K/V 字节比较和三帧连续整链图重放均逐字节相同。540p B-C-C-B、80 帧／段的整链中位数为 **53.256→53.235 ms（−0.021 ms）**，在波动内。Astra 对编译产物的只读审计发现，首版点积后四次 `tl.gather` 引入大量布局重排。按它的具体指导，隔离的 [`v2`](../game/c64_qkv_direct_pack_v2.py) 仅把通道拆分改为现役内核已使用的静态 `_halves`；540p 编译中间代码的 `ttg.convert_layout` 从 18 处减到 5 处，LLIR 的 shuffle 行从 177 减到 113、barrier 行从 42 减到 16。这些是静态代码计数，非时间。

v2 的三档局部 Q/K/V 和三帧连续图重放整链也逐字节相同。540p QKV 生产段的配对图计时中位数为：现版 **0.427 ms**、首版 **0.468 ms**、v2 **0.209 ms**（每段 120 次重放）。但只替换一个 C64 块时，540p 完整 `modes.process` B-C-C-B、120 帧／段中位数只从 **53.398→53.312 ms（−0.086 ms）**，两组配对分别 −0.111／−0.077 ms；480 个计时帧逐帧 RGB 哈希一致。360p 为 **27.418→27.447 ms（+0.029 ms）**，两组配对均略慢；480p 为 **39.010→39.030 ms（+0.020 ms）**，配对方向相反。这两档同样每段 80 帧、逐帧字节一致。局部收益明确，单块整帧收益只在 540p 显出微小改善，**目前不部署，也不直接将单块收益乘以块数**。扩展到其他 C64 实例前，应确认三档的累计前景及空间布局代价。

### 八块累计试验

按 Astra 指定范围，将同一 v2 算术核安装于 C64 编码器四块及对应解码器四块，保持每块原有窗口移位、原注意力与后续计算。隔离实现为 [`c64_qkv_direct_pack_all_v1.py`](../game/c64_qkv_direct_pack_all_v1.py)。三档各八块 Q/K/V 逐字节门、三帧重置→历史图重放完整输出逐字节门均通过；捕获时每块六次调用，未误入其他网络块。之后每档 B-C-C-B，每段 16 帧预热＋80 帧计时，所有 320 个对应 RGB 帧逐帧哈希一致，计时仅用 D 盘预编译缓存及 `DiskOnly`。

| 档位 | 基线中位数 | 八块候选中位数 | 差值 | 两组配对差值 |
|---|---:|---:|---:|---:|
| 360p | 27.038 ms | 26.766 ms | **−0.273 ms（−1.01%）** | −0.201／−0.293 ms |
| 480p | 38.520 ms | 37.919 ms | **−0.601 ms（−1.56%）** | −0.641／−0.582 ms |
| 540p | 53.293 ms | 51.769 ms | **−1.525 ms（−2.86%）** | −1.579／−1.506 ms |

540p 的 P95 54.138→52.482 ms、CV 0.87%→0.63%；360p 的 CV 1.24%→2.07%，故不能称三档波动均改善。此收益不能与上方 C32＋post 的收益直接相加；尚需三项同轮组合配对、预编译和游戏内稳定性验证，当前仍是 E 盘隔离候选，未写入 G 盘便携包。
