# 1080p 图执行与共享临时内存（2026-09-09）

后续已完成注意力步长读取、窗口重排融合和新一轮精确/快速验证，见 `WINDOW_LAYOUT_STATUS.md`。本文件保留共享图池这一轮的结果。

当前适配器为 `graph_front_v6.GraphFront`：计算与捕获继承 v5，v6 只修复关闭会话后 `last_entry` 继续持有输入/输出缓冲的问题。当前仍为实验性、单拥有者、串行调用接口。35 个主后端源文件和精确检查点 736 未变，生产集成未完成。

v5 让重置和连续帧图共用一个会话专有的捕获流及临时内存池。输入、模型常量、私有历史、调用方结果均在池外；每张图还把本次完整结果复制到自身的池外输出缓冲，然后沿用原来的返回值复制和完成检查。捕获后检查持久输入/输出地址不落在共享池内。原 MotionNR 仍逐帧处理种子、噪声、运动及历史，模型算术没有改动。

1080p 的两张图原本各保留 3,210,739,712 字节，共 6,421,479,424 字节。共享后合计为 3,210,739,712 字节。这是图池大小，不是整个进程显存。原配对进程使用共享显存约 2.37GB；共享池测试的采样为约 97.5MB。Windows 数据是运行中的单次采样，不是连续峰值记录。

最新配对测试每种精度使用两个独立模型，预热重置与连续帧路径后进行两轮 13 帧，交替执行顺序。比较完整 RGB、私有历史、重置、种子、输入/输出所有权、非法运动拒绝，以及另一张图已发布输出的完整字节。每种精度 52 次输出；三种精度共 156 次。随后独立复读全部保存输出及原生 RGB，并核对作业退出码 0。

| 精确算术 | 1902.981 ms | 1879.043 ms | 1.013× |

上述计时包含完整模型调用、同步、动态前端、图输入与结果复制、模型常量检查和私有历史；排除上传、编译/捕获、验证及 IO。每种精度在独立进程内配对测试，不能把 FP16 与 INT8 的约 2% 数字差当成严格的精度间胜负。两轮图均值分别为：精确 1877.700/1880.386ms、FP16 652.746/654.446ms、INT8 641.811/638.595ms。首次 FP16 1080p 预热约 104.85 秒，包含新尺寸编译，不在稳定帧计时内。当前速度仍远离实时游戏需求。

精确模式全部输出与固定 4060 参考的 RGB32F 字节一致；另已完成 480p 精确图执行 v3 的两轮 52 次原生字节比较，477.813→432.065ms。后者使用旧的独立图池版本，不能混作最新适配器的配对速度。

1080p 快速输出在普通执行、图执行与重复轮之间逐字节一致，但与原生精确结果不同。12 个真实相邻帧的聚合 PSNR 为 FP16 54.609dB、INT8 46.401dB，最低单帧为 52.465/45.814dB；最大分量绝对误差为 0.104980/0.107910（原始浮点值）。没有缩小模型输入分辨率。助手检查了源帧 191 的整图与赛车局部，未见明显结构破坏；这不构成长时序或用户画质验收。

这组原生参考仅包含源帧 180–191，再重复首帧重置，约 0.2 秒实际运动。1080p 源视频实测为 1920×1080、60000/1001fps、390 帧，按帧数约 6.5065 秒（ffprobe 容器时长 6.505 秒）。下一次人工审核应准备足够长的对照，不再提交这段短片作为长时序验收。审核图和统计位于 D 盘 `results/graph-native-1080-review-v1`。

最新 v6 还分别重跑了已获用户批准的完整 243 帧 480p 视频：FP16、INT8 均连续使用自身历史，完整输出、私有历史、输入与种子全部符合原批准数据，末尾重置复现。保留第 0、120 帧结果到最后，后续重放没有覆盖它们。两种模式分别正常退出，保存数组独立复读通过；复用原无损数组，没有新增视频或长片输出副本。用户的“两种快速模式都可接受”审核继续有效。

单模型 480p 长片本轮统计：FP16 分配峰值 865,459,712 字节、保留峰值 1,637,875,712 字节；INT8 分别为 1,164,018,176 和 1,929,379,840 字节。每会话共享图池 731,906,048 字节，INT8 另持有 147,185,664 字节量化权重。不是生产显存预算；测试还持有特定旧输出用于所有权检查。

INT8 定向保护测试验证了外部权重缓存改写/释放、软件注入完成异常后的不推进状态与重试、模型常量变动拒绝。v6 关闭测试使用弱引用核对最后图的前端与输出张量已释放，并检查重复 close。该测试不是实际 GPU 故障注入，物理驱动缓存释放也不由弱引用证明。

版本与失败记录：

- `validate_graph_native_v1.py` 使用独立池 v3。480p 精确正常，1080p 正确性也通过，但普通执行因显存压力升到约 8 秒，3.76× 的比例不作为可靠的模型加速结论。
- `validate_graph_native_v2.py` 增加预热后 empty_cache 与内存记录，仍保留两份大图池，未解决问题。保留原始记录，不采用其 3.88× 比例。
- `graph_front_v4.py` 首次共用图池；较短 INT8 保护测试通过，但原生 1080p v3 测试在末尾重置时捕获到另一张图内部输出被覆盖，退出 1。该版本不可作为最终候选；`validate_graph_long_v2.py` 未执行。
- `graph_front_v5.py` 加入池外专用输出，1080p `validate_graph_native_v4.py` 三种精度全部通过，包括此前失败的重置位置。
- `graph_front_v6.py` 仅修正关闭引用持有，不改 v5 计算路径；保护测试与两种完整 243 帧复测均实际通过。`validate_graph_long_v3.py` 使用 v6。
