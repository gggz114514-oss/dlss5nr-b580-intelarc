# 当前 FP16 矩阵分块优化（2026-09-09，本地）

在已有的历史采样、ViT QKV 和 K8 优化基础上，对当前实际通用 FP16 矩阵调用按尺寸选择分块。固定 NR 输入 256×256 的完整调用对照中，连续帧平均耗时从 13.929848 ms 降到 13.296283 ms，减少 0.633565 ms（4.5483%）。720 次完整输出和独立 390 帧连续序列验证通过，没有新增画质变化。

此项成果只保存本地，不更新公开仓库或 Release。正式精确后端的 35 个文件不变；FP16 快速路线相对 NVIDIA 的既有、已获用户接受的差异仍存在。此次字节一致是相对优化前及已批准的快速路线，不是宣称 FP16 快速模式与 NVIDIA 原生已经字节一致。

## 明确输入尺寸与计时范围

用户本轮询问是否在与原生 480p 比较。近期性能目标和倍数比较使用的是双方相同的 **256×256 NR 输入**。源画布为 1080p 的视频展示采用 NR256 后残差合成，不能标成原生 480p 或原生 1080p 模型性能。

| 固定参考的 NR 实际输入 | RTX 4060 原生连续帧完整调用 |
| --- | ---: |
| 256×256 | 3.566807 ms |
| 864×480 | 4.619159 ms |
| 1920×1080 | 14.121662 ms |

上述是已有固定运行库和固定样本的记录，不是本轮重新测得的不同场景平均值。来源为 `experimental/native-steady-bench-v1/validation.json`，SHA256 `70a86900dbde71d285f187cedc42a123bc7706cf27f21f0231e515b4d964659d`。

当前 B580 同一 NR256 输入、显存驻留输入、完整主机调用加完成等待的耗时，为该 4060 参考的 3.727783 倍。没有按 480p 或 1080p 的原生数字计算这个倍数。完整 NR 计时排除上传、运动估计、解码、残差缩放、呈现和游戏竞争；设备事件区间也不能与这个完整主机调用口径混用。

## 从实际剩余调用选择分块

先用当前全部融合组件预热模型，随后在计时和图捕获之外执行一次实际连续帧主体，采集尚经过通用矩阵实现的输入、权重、初始累加器及完整输出。最终 NR 输出与固定参考一致，历史和 seed 未变化。

采集到 34 种尺寸/布局类别，共每帧 167 次通用 FP16 dense 调用。每类保留一个实际操作数集合，记录原始 shape/stride；基准重建原始跨度，包含原来实际需要的连续化副本。各类别原始数据累计 109,174,784 字节（包含输出，可能重复计入共享数据），低于固定 128 MiB 上限；保存后审计复读 116 个唯一数组、77,762,003 存储字节。文件位于 D 盘内容寻址存储中。

所有类别都测试 8 组 M/N 分块；固定 BK32、4 warps 和原 `fast_matrices_v3._matmul`，不改 K 归约顺序、精度、half 输出或初始累加规则。272 次完整矩阵输出比较全部匹配，另核对捕获输出、各计时组末尾输出、输入不变及图池外持久输入输出。

计时为五轮顺序轮换/反转，每图四次调用、每组十次图重放。只有中位数至少减少 5%、且每轮都至少快 2% 的配置才可入选。17 种类别选出新分块，覆盖每帧 83 次调用；其余 84 次保留原分块。局部计时按调用次数加权估算节约 0.527540 ms，不将这个估算直接当作整帧收益。

## 实现与回退

`current_dense_tiled_provider_v1.py` 继承已有 `K8TiledMatrices`，用只读固定表选择上述 17 种类别，调用已有 `dense_tiles_v1.dot`。仅选择所属模型的完整二维 half 权重、已观测输入布局、FP16 快速模式及 K16 调用；其他类别、精度、权重与原始 K8 计算沿用父实现。没有推理时自动调参或新增量化。

权重键包含设备、dtype、地址、shape 和 stride，并保留模型权重引用；现有完整模型常量身份/版本和图所有权检查仍生效。分块表不是可变的运行时设置。组件仍用于现有串行实验会话，不宣称支持多个生产会话并发修改全局作用域。

验证每种入选类别在真实模型权重上实际命中新路径，并比较完整输出。另验证未拥有的权重、未知行数、非连续输入、FP32 输入、新初始累加器和 INT8 模式六条回退路径，结果与父实现一致。完整模型的进度回退中，新路径实际命中 17 类、合计 83 次。

## 完整流程收益与验证

| 测试口径 | 同轮上一版 | 新分块 |
| --- | ---: | ---: |
| NR256 完整调用，连续帧 | 13.929848 ms | 13.296283 ms |
| NR256 完整调用，重置帧 | 13.653985 ms | 13.056770 ms |
| NR256 + 1080p 残差合成，连续帧 | 14.698321 ms | 14.074030 ms |
| NR256 + 1080p 残差合成，含重置 | 14.690631 ms | 14.066262 ms |

NR256 连续帧的三轮均值：旧版 13.951658 / 13.947650 / 13.890235 ms，新版 13.310202 / 13.286877 / 13.291770 ms，三轮均有收益。上一轮记录的绝对耗时来自另一次运行；提速百分比使用本轮配对结果，避免将运行间波动归因于改动。

- 17 组真实权重的组件调用及 6 条回退全部通过。
- 78 个完整 NR 和 1080p 合成输出通过，独立历史、重置、调用方所有权、进度回退、非法运动及表变化拒绝检查通过。
- 390 帧独立连续历史通过：每帧完整低分辨率 NR 字节与完整 1080p FP32 输出哈希均匹配已批准的视频记录，末尾重置复现首帧。不生成新视频或完整大帧转储，按用户豁免无需再次肉眼审核。
- 720 次与原生参考相同输入的完整 NR 输出比较通过，同时匹配冻结 Triton 3.7.2 快速路线的对应哈希。输入、LUT、持有输出及图所有权检查通过。

长序列审计重读 780 个引用数组、2,503,020,263 存储字节。保存后审计认证实际 GPU 比较收据和文件内容，不是独立 CPU 模型重算。图构建阶段记录 498 次新分块调用（83 × 6 次主体构建执行）；这不是整段视频实际只有 498 次该类 GPU 运算，后续帧通过图重放执行。

## 后续方向

本次已完成该分块改动的必需验证。剩余主体诊断完成时间仍约 11.43 ms，仍需改善。一个值得验证的方向是 cubic 激活目前使用的补偿 half FMA：`triton_cubic_fp8.py` 和 `fused_branched_mlp_v1._cubic` 的三个系数都是可精确表示的 half 常数，可测试在这些特定调用点改用原生 half FMA，先逐位检查全部 65,536 个 half 输入与认证的 cubic+FP8 表，再测实际融合 MLP 和完整流程。

这只是已从当前代码确认的待测方向，没有声称等价或提速已经成立；不能全局替换通用 `_half_fma_value`。需保留 clamp、两次 half 舍入、最后乘法、FP8 边界和非有限值语义。整个目标仍包括正式精确行为、更多尺寸/HDR/控制、生产 OptiScaler/XeSS/ComfyUI 接口与性能持平，当前 NR256 快速组件不替代这些要求。
