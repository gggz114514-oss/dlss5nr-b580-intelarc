# 决定逐字节一致的数值规则和布局

这里列出固定SF-v2/SM89参考的实验结果，不将它们宣布为所有NVIDIA GPU的通用硬件规范。公式来自本次隔离测量和实际源码；相关历史收据见[证据索引](../evidence/index.json)。

## 1. 权重位置正确，运算结构仍可能错误

pre的QKV实际起点为`0x2460`，不能沿用公开恢复图中的`0x2450`。更大的区别发生在C64：普通64→224→64 MLP候选的MAE约8.945；实际是两条独立分支，每条读取同一原输入：

```text
64 → 128 → cubic → FP8 → 32 → FP8 → 64
```

两条结果依次加到half残差；初始残差为`half(input * scale)`。32通道收缩之后没有第二次cubic，误加一次仍有约0.794 MAE。C128/C256后来分别验证为4/8条对应分支，不能只根据通道数猜测后就直接宣称完成。

C512同样不是通用门控MLP：先做全512投影和FP8，再拆8组64通道，各做64→256→cubic→FP8→64→FP8，拼回512后再做全投影。ViT又有不同的split-K与归一化顺序。实现分别见[multihead_block.py](../backend/nr_backend/multihead_block.py)、[split_block.py](../backend/nr_backend/split_block.py)、[vit_block.py](../backend/nr_backend/vit_block.py)。

## 2. FP8边界是运算的一部分

同一数学表达式在不同位置量化会产生不同结果：

- pre/C32部分残差保留未量化MLP结果；C64注意力残差来自已量化FP8结果，因为原生从共享内存重载。误用未量化结果曾造成83,560个整块错误字节。
- pre down从未量化输出做half的2×2池化，再乘0.25并量化FP8。先量化skip再池化，在gradient中会产生167,253个错误字节。
- FP8转换要保留负零。某条XPU转换路径丢失负零，故显式保留符号；诊断序列化也不能再用会改变符号的路径编码一次。

pre池化次序为：

```text
half(half(topLeft + topRight) + half(bottomLeft + bottomRight))
→ half(value * 0.25) → FP8
```

测试比较原始字节，所以`+0`和`-0`也可能构成差异；仅使用数值相等或allclose会漏掉它。

## 3. 普通矩阵乘法不能自动复制原生累加

原生矩阵路径在固定K组上按操作数指数对齐、截断、求和，随后舍入到half，再进入下一K组。我们以整数对齐和求和复现这些边界。

- HMMA：观察到K8组，按操作数指数之和的公共最大值对齐，保留24位小数有效位后向零截断。
- QMMA相关路径：K16组，13位小数有效位。
- E4M3次正规操作数的对齐指数保留格式指数-6；不能简单取`floor(log2(abs(x)))`。这一差异曾留下191个half投影差异和5个FP8 skip差异。
- ViT部分投影拆为独立K分区，残差只放第0分区，再按half次序合并，不能先把所有分区按FP32加完再舍入。

CPU任意精度整数/独立数值oracle用于验证舍入，再把可行实现放到B580。B580不需要具备FP64才能运行精确后端。当前[参考算术](../backend/nr_backend/tensor_math.py)及[Triton算术](../backend/nr_backend/triton_math.py)保留相关规则。这种正确性实现与INT8模型量化是两件不同的事。

## 4. 一个half FMA中点如何破坏1080p对齐

1080p的decoder call156在输入完全一致时有73个FP8输出字节不同。进一步比较：

| 边界 | 完整比较规模 | 修正前差异 |
| --- | ---: | ---: |
| MLP half输出 | 4,669,440值 | 0 |
| QKV half投影 | 14,008,320值 | 0 |
| 完整K和前32个Q的归一化输出 | 7,004,160字节 | 1 |
| 前32个查询的指数 | 4,669,440值 | 25 |

唯一错误K位于一个归一化分母。关键计算是：

```text
fma_half(-6.125, -6.125, half(2^-20))
精确乘积 = 37.515625，恰好是half中点
加入2^-20后应向上舍入为37.53125
先用FP32相加可能丢失该微小加数，转half则得到37.5
```

因此“先FP32算完，再转half”不等于真正的half融合乘加。修正使用TwoSum保存加法残差，在half中点决定舍入；随后用以`2^-48`为单位的Python整数oracle验证24007组样例和1080315个跨分批边界案例，CPU/B580都为零差异。这里不是穷举全部half三元组的证明。

[fma_witness.py](../tools/fma_witness.py)用标准库重现这个反例；[check_half_fma.py](../tools/check_half_fma.py)将独立整数oracle与已发布实现比较。修复针对算术规则，未读图像坐标或缓存失败窗口结果。

## 5. 注意力并不是标准softmax

Swin指数近似的观察规则：half融合乘加`score * .044921875 + 1.30078125`，clamp到`[1.03125,1.5693359375]`，再对half位型执行`(bits << 5) + 0x8000`并截断16位。

64项和保留原生分组及每一步half舍入；分母钳位、倒数转half、与指数相乘和FP8量化也有明确顺序。不能直接替换为框架的`softmax`。

ViT有不同的指数近似：V乘积使用量化指数，而分母使用未量化指数，乘V之后才归一化。它不是Swin的一份简单大尺寸拷贝。相关实现见[attention.py](../backend/nr_backend/attention.py)和[vit_block.py](../backend/nr_backend/vit_block.py)。

## 6. 物理布局必须独立证明

原生buffer不总是逻辑HWC。pre skip采用quad布局`[H/4,W/4,32lanes,4words,4bytes]`；down采用split-C16，16通道内顺序是`0,1,8,9,2,3,10,11,4,5,12,13,6,7,14,15`。C64多头、C512池化、ViT的布局又不同。

采用多输入的寄存器列与逻辑像素/通道对应关系恢复布局，检查映射唯一、无缺失，再把计算结果重新编码回完整物理buffer比较原始字节。C64输入映射验证了全部4096个寄存器列；half FMA失败窗口的布局由另外90个CTA建立，未针对那个失败点拟合。

## 7. 查表覆盖标量域，不缓存画面

原生噪声所用radius/sin/cos、sigmoid、MUFU倒数涉及硬件近似。精确路径选择枚举相应标量输入域，并在B580上做索引及后续计算：

| 表 | 域/规模 | 限制 |
| --- | --- | --- |
| 噪声radius/sin/cos | 各2^24个FP32值，合计192MiB | 与图像、帧内容、特定seed无关 |
| sigmoid | 全65536种half编码，256KiB | 固定SM89参考 |
| 历史归一化倒数 | `[0.96875,1.15625)`内1,835,008个FP32值 | 超出记录域拒绝 |
| 尺寸倒数 | 整数1..4096，16KiB | 不自动扩展输入尺寸合同 |

历史倒数域有279,767项与正确舍入FP32倒数相差1 ULP；尺寸倒数中有519项不同。直接替换为`1/x`会在临界输出处留下差异。这些表并不存储模型特征、上一帧或最终图像；完整推理使用自己的输入和历史。
